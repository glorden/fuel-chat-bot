# Архитектура

## Пайплайн

```
Long Poll (vkbottle) → фильтр себя/дублей → команды в чате? (!вкл/!выкл — ADMIN_ID;
    !лимит/!лимиты — все) → обрабатываются и выходят, дальше не идут
  → склейка контекста (fwd_messages/reply_message — структурно, rule-based+LLM;
    предыдущее сообщение автора из in-memory кэша — только LLM) → pre-filter (тема?)
  → классификация+извлечение+резолв станции (LLM, если LLM_ENABLED и доступен; иначе/при сбое — rule-based)
      → отчёт: запись в БД (fuel_report/station_break/fuel_limit — все append-only, пишутся только если есть сигнал)
      → вопрос: факты по станции (марки + перерыв + лимит) → рендер шаблона
          → если станция не резолвилась, но вопрос похож на "сколько лимит на <бренд>" —
            статичный лимит бренда из gazetteer.yaml, в обход резолва станции
          → (если триггер сработал) отправка ответа
```

Генерация текста ответа — всегда через `templates.py`, независимо от того, кто делал разбор (LLM или regex). Это единственная защита от галлюцинаций: бот физически не может «нафантазировать» несуществующую АЗС или статус — шаблон использует только то, что реально есть в базе или в `gazetteer.yaml`.

## Компоненты

- `bot.py` — точка входа: инициализация `vkbottle.Bot` (**обязательно** `bot.labeler.message_view.replace_mention = True`, иначе `message.is_mentioned` всегда `False`, без ошибки — см. «Триггеры ответов»), запуск Long Poll.
- `config.py` — настройки из env: `VK_TOKEN`, `GROUP_ID`, `ADMIN_ID`, пороги свежести, `AUTO_REPLY_ON_QUESTION`, debounce, LLM-флаги.
- `vk_handlers.py` — обработчик `message_new`: отсечение собственных сообщений бота, идемпотентность, разбор команд `!вкл`/`!выкл`/`!лимит`/`!лимиты` (до пайплайна, см. «Команды в чате»), склейка контекста (`_quoted_context_text`, `_last_author_message` — только для LLM-ветки), диспетчеризация в пайплайн, отправка ответа (тег адресата, debounce).
- `pipeline/prefilter.py` — быстрый keyword-фильтр по теме (марки/бренды/типовые слова + голое «?»).
- `pipeline/extract.py` — regex-извлечение: марка+статус, очередь, технический перерыв, лимит отпуска; классификация отчёт/вопрос/нерелевантно. Rule-based путь и фолбэк для LLM-пути.
- `pipeline/resolve_station.py` — сопоставление текста с АЗС из `gazetteer.yaml` (бренд+локация), брендовые статичные лимиты (`get_brand_fuel_limit`, `get_displayed_brand_fuel_limits`). Rule-based путь и фолбэк для LLM-пути.
- `pipeline/facts.py` — дата-классы `StationFact`/`StationBreak`/`StationLimit`, общий `MOSCOW_TZ`.
- `pipeline/pipeline.py` — `_analyze()`: LLM первым (если включён), при `None` — rule-based без изменений; `process_message()` — оркестрация записи в БД и ответа на вопрос (включая брендовый фоллбэк по лимиту).
- `pipeline/qa.py` — `answer_question()` (факты+перерыв+лимит по резолвленной станции), `answer_brand_limit_question()` (лимит по бренду без резолва станции).
- `llm/client.py` — диспетчер по `config.LLM_PROVIDER`, реэкспортирует `LLMAnalysis`/`_parse_arguments`.
- `llm/schema.py` — провайдер-агностичное ядро: схема полей, валидация ответа модели (включая проверку `station_id` через `is_known_station`).
- `llm/groq_client.py` / `llm/gemini_client.py` / `llm/mistral_client.py` — по одному вызову `raw_analyze(text) -> dict | None` на провайдера; `gemini_client.py` дополнительно конвертирует схему в нативный диалект Gemini.
- `llm/prompts.py` — системный промпт + `_stations_brief()`, который читает `gazetteer.yaml` заново при каждой сборке промпта (не кэширует на импорте, в отличие от `resolve_station.py`).
- `templates.py` — `render_station_answer` (компактный формат: марки с одинаковым статусом на одной строке, один timestamp в заголовке), `render_brand_limits_list` (для `!лимит`).
- `db/schema.py`, `db/repo.py` — SQLite: `fuel_report`, `station_break`, `fuel_limit`, `auto_reply_setting`, `unresolved_mention`, `processed_message`. Идентичность станций в БД не хранится — единственный источник правды это `gazetteer.yaml`, в БД станция — просто `station_id`.
- `gazetteer.yaml` — вручную поддерживаемый список известных АЗС (id/название/бренд/адрес/алиасы) + `brand_fuel_limits`/`brand_fuel_limits_display`.
- `scripts/review_unresolved.py` — CLI: нераспознанные упоминания станций по частоте.
- `scripts/compare_llm_vs_rules.py` — сравнение LLM vs rule-based на фикстурах.
- `tests/` — pytest на чистых функциях пайплайна, фикстуры из реальных обезличенных сообщений.

## Модель данных

Всё в БД — **append-only логи**, ничего не перезаписывается (кроме `processed_message`, чисто дедуп). «Текущее состояние» всегда вычисляется на лету при запросе, не фоновой задачей:

- **`fuel_report`** — факт «марка X доступна/недоступна» на станции. Несколько отчётов подряд — подтверждение, не дубликат; если два недавних противоречат друг другу, это явно отражается в ответе.
- **`station_break`** — технический перерыв (слив/отстой/тех. перерыв) целиком по станции, не по марке. `qa.py::_latest_break` — **без окна активности**: последняя запись показывается всегда, с возрастом, без автодеактивации по таймауту.
- **`fuel_limit`** — факт «на станции лимит N л / без ограничений», **из чата**, привязан к конкретной станции. Та же логика «без окна активности», что у `station_break`.
- **`auto_reply_setting`** — состояние переключателя `!вкл`/`!выкл` (см. «Команды в чате»). Та же append-only форма.

Ответ по станции показывает факты по маркам, перерыв и лимит **вместе**, один вид факта не подменяет другой.

Идентификация станции — по курируемому `gazetteer.yaml`, не по свободному тексту: `brand_aliases`/`location_aliases` матчатся независимо (`resolve_station.py`) — бренд с одной точкой резолвится по одному алиасу, бренд с несколькими точками — только если в тексте есть ещё и алиас локации; голое упоминание многоточечного бренда без локации уходит в `unresolved_mention`, если только это не единственный упомянутый бренд у которого задан `default_for_brand`. Отдельный запасной путь — резолв по одной лишь локации, если её алиас уникален по всему газетиру.

**`gazetteer.yaml::brand_fuel_limits`** — статичный лимит "в одни руки" **по бренду**, известный заранее (НЕ факт из чата, не то же самое, что `fuel_limit`). Нужен отдельно, потому что у многоточечных брендов голый вопрос без адреса ("сколько на РН?") не резолвит конкретную станцию, а лимит на неё всё равно нужно как-то показать — `answer_brand_limit_question()` отвечает лимитом бренда напрямую в обход резолва станции. Каждая запись — `{status: limited, liters: N}` или `{status: unlimited}`. `brand_fuel_limits_display` — курируемое подмножество брендов для команды `!лимит` (не обязательно совпадает со всем `brand_fuel_limits`).

**Известное, не исправленное ограничение**: и LLM, и rule-based поддерживают только один `station_id` на сообщение — сообщение про две станции сразу теряет факты по одной или уходит в `irrelevant`. Чинить — менять форму `ExtractResult`/tool schema на список станций, не однострочная правка.

## Триггеры ответов

Ответ на вопрос отправляется, если бота явно упомянули **или** включён автоответ (флаг `AUTO_REPLY_ON_QUESTION` из `.env`, переопределяемый в БД командой `!вкл`/`!выкл` — см. ниже), плюс debounce (`MIN_REPLY_GAP_SECONDS`) как страховка от флуда.

**Важный нюанс vkbottle**: `message.is_mentioned` без `bot.labeler.message_view.replace_mention = True` в `bot.py` всегда `False`, без ошибки. Найдено только на живом тесте.

**Молчание вместо шаблонного «не знаю»**: если станция не распознана, или распознана, но по ней вообще нет фактов (ни марок, ни перерыва, ни лимита), `answer_question` возвращает `None`, ответ не отправляется — никакого «не понял»/«нет данных» в чат.

### Команды в чате

Разбираются в `vk_handlers.py` до основного пайплайна (не идут через `is_on_topic`/классификацию/LLM) — голый текст сообщения целиком, без хвостов, регистр и пробелы по краям неважны.

- **`!вкл` / `!выкл`** — переключают `AUTO_REPLY_ON_QUESTION`. Доступны только `ADMIN_ID` (проверка по `from_id`). Состояние — в БД (`auto_reply_setting`), переживает рестарт/редеплой; `.env`-значение остаётся дефолтом, пока командой ни разу не пользовались.
- **`!лимит` / `!лимиты`** — статичный список лимитов по `brand_fuel_limits_display`. Доступна всем, без проверки `ADMIN_ID`, но с тем же debounce, что у обычных ответов (открыта всем — риск флуда реальнее, чем у admin-only команд).

## LLM-анализ (опционально, `LLM_ENABLED`, `LLM_PROVIDER`)

Классификацию+извлечение+резолв станции можно передать LLM вместо `extract.py`/`resolve_station.py` — тремя провайдерами на выбор (`mistral` по умолчанию, либо `groq`/`gemini`), через forced tool calling с общей схемой (`llm/schema.py`). При любом сбое (лимит/таймаут/невалидный ответ) — прозрачный откат на rule-based; ответ модели валидируется перед использованием (неизвестные значения молча отбрасываются, а не ломают разбор). Полная история выбора и сравнения провайдеров, живые проверки, конкретные цифры совпадения — в **PROGRESS.md, Этапы 4-6, 15-18**.

**Провайдеры:**
- **Mistral** (`ministral-8b-2512`, по умолчанию с Этапа 18) — лимит по токенам/запросам **в минуту**, не по дням как у Groq; не требует SOCKS5-туннеля с library-vps (в отличие от Groq/Gemini — см. DEPLOY.md).
- **Groq** (`llama-3.3-70b-versatile`) — был дефолтом до Этапа 18; дневной лимит токенов (100k) реально исчерпывался на живом трафике в течение вечера.
- **Gemini** (`gemini-flash-lite-latest`) — лимит по RPM (~8-9/мин на бесплатном тарифе); через SOCKS5-туннель бота **не работает** (Google блокирует и сам внешний узел туннеля, не только российские IP) — на library-vps не используется.

Для всех трёх — датированная модель, не алиас `-latest`: `mistral-medium-latest`/`gemini-flash-latest` резолвятся в модели с заметно более тесными лимитами, чем нужные датированные версии.

**Открытый, не устранённый риск — модель может сфабриковать факт, не только ошибиться со станцией.** На реальном сообщении Groq в 4 из 6 повторов придумал недоступность марки, которой в тексте не было вообще. Это не «сбой» (ответ формально валиден) — существующая валидация ловит только заведомо невозможные `station_id`, не выдуманные `reports`. `queue_note` у LLM-пути — тоже слабое звено: проверяется только что это непустая строка, свободный текст модели уходит в чат почти без фильтра. Отдельно, не баг конкретно LLM, но усилившийся риск с Этапа 26/29: **включённый `!вкл` делает любую ошибку резолва станции видимой сразу всему чату**, а не только тем, кто явно тегнул бота — живой пример см. PROGRESS.md, Этап 28 (Mistral уверенно приписал вопрос не той станции Роснефти).

## Деплой

Подробности — в [DEPLOY.md](DEPLOY.md). Кратко: Docker Compose на library-vps (геолоцирован в России), два сервиса — `app` и `ai-proxy` (SOCKS5-туннель для Groq/Gemini, которых Mistral не требует). `bot.db`(+`-shm`/`-wal`) и `gazetteer.yaml` — bind-mount с хоста, переживают пересборку образа; Python-код — нет, нужен `--build` при изменениях в `.py`. Секреты — через `.env`, ключ туннеля — через `secrets/` (не коммитятся).

## Известные пробелы и открытые вопросы

- **Один `station_id` на сообщение** — см. «Модель данных» выше.
- **LLM может сфабриковать факт** — см. «LLM-анализ» выше.
- **Ретрай без бэкоффа на persistent-ошибках VK API** (найдено на Этапе 21 — бот ~3 часа долбил `groups.getLongPollServer` раз в секунду при бане сообщества, пока не заметили и не остановили вручную). Не починено — кандидаты: бэкофф в обработке ошибок long poll, уведомление при затяжной серии одинаковых ошибок через канал, не зависящий от VK (сам VK не может пожаловаться на свой же сбой).
- **Схема `FuelReport` не поддерживает факт про очередь без марки топлива** — LLM такие иногда находит, но писать некуда.
- **`_BREAK_KIND_WORDS`/промпт не покрывают все синонимы перерыва** — например «закрывается»/«были закрыты» не распознаются ни rule-based, ни (в контексте чата) LLM-путём.
- **Префильтр не знает про все локации газетира** — только явные бренды/марки плюс два точечных исключения («вилга», «стк» — единственные точки своего бренда, добавлены по факту живых сообщений). Остальные голые локации без бренда/цифры мимо анализа не проходят. Не расширяли на весь газетир осознанно — часть алиасов локаций (например «магнит», «правда») это обычные бытовые слова.
- **Короткие реплики в диалоге** («Есть.», «это на силикатном?») иногда классифицируются LLM как `question`, когда процитированный контекст содержит «?» — путает «вопрос где-то в контексте» с «текущее сообщение — вопрос». Эффект мягкий (гвард не даёт записать как отчёт).
- **Long Poll → Callback API**, если бот когда-нибудь расширится на несколько бесед/городов; тогда же пересмотреть SQLite в пользу БД с нормальной поддержкой многопроцессной записи.
- **OCR/vision-анализ фото** ценников и очередей — не делали, провайдеры (Groq/Llama) технически умеют мультимодальный ввод.
