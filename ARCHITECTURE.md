# Архитектура

## Пайплайн

```
Long Poll (vkbottle) → фильтр себя/дублей → pre-filter (тема?)
    → классификация+извлечение+резолв станции (LLM, если LLM_ENABLED и доступен; иначе/при сбое — rule-based)
        → отчёт: запись в БД (append-only)
        → вопрос: выборка свежих фактов → рендер шаблона → (если триггер сработал) отправка ответа
```

Генерация текста ответа — всегда через `templates.py`, независимо от того, кто делал разбор (LLM или regex). Это единственная защита от галлюцинаций: бот физически не может «нафантазировать» несуществующую АЗС или статус — шаблон использует только то, что реально есть в базе.

## Компоненты

- `bot.py` — точка входа: инициализация `vkbottle.Bot`, запуск Long Poll.
- `config.py` — настройки из env: `VK_TOKEN`, `GROUP_ID`, `ADMIN_ID`, пороги свежести данных, `AUTO_REPLY_ON_QUESTION`, настройки debounce.
- `vk_handlers.py` — обработчик `message_new`: отсечение собственных сообщений бота (`from_id == -GROUP_ID`), проверка идемпотентности, диспетчеризация в пайплайн, единая точка отправки ответов (debounce/rate-limit).
- `pipeline/prefilter.py` — быстрый keyword-фильтр по теме (бензин/азс/заправ-/очеред-/марки топлива/geo-вложение/фото).
- `pipeline/extract.py` — regex/keyword-извлечение марки топлива, статуса наличия, длины очереди; классификация отчёт/вопрос/нерелевантно. Rule-based путь и фолбэк для LLM-пути.
- `pipeline/resolve_station.py` — сопоставление упоминания с известной АЗС: матчинг «бренд + локация» по алиасам из газетира (см. «Модель данных»), иначе — запись в `unresolved_mention`. Rule-based путь и фолбэк для LLM-пути.
- `pipeline/pipeline.py` — `_analyze()`: если `LLM_ENABLED` — сначала `llm.client.analyze()`, при `None` (сбой/лимит/невалидный ответ) — `extract()`+`resolve_station()` без изменений. См. «LLM-анализ» ниже.
- `llm/client.py` — обёртка над Groq (`groq` SDK, tool calling): классификация+извлечение+резолв станции одним вызовом, валидация ответа, `None` при любом сбое.
- `llm/prompts.py` — системный промпт для Groq: правила разбора, полный газетир (включая алиасы) как контекст, few-shot примеры.
- `pipeline/qa.py` — для вопроса: выборка последних фактов по станции/марке, расчёт свежести (tier: свежо/устарело/нет данных) на момент запроса, рендер ответа через шаблоны.
- `templates.py` — русские шаблоны ответов: свежие данные / устаревшие / нет данных / противоречивые данные / станция не распознана.
- `db/schema.py`, `db/repo.py` — SQLite: `fuel_report`, `unresolved_mention`, `processed_message`. Идентичность станций в БД не хранится — единственный источник правды по станциям это `gazetteer.yaml` (см. ниже), в БД станция — это просто `station_id` (строка-ключ из газетира).
- `gazetteer.yaml` — вручную поддерживаемый список известных АЗС (id, название, бренд, адрес, алиасы). Загружается в память при старте, отдельных таблиц `Station`/`StationAlias` в БД сознательно нет — дублировать источник правды незачем.
- `scripts/review_unresolved.py` — CLI: нераспознанные упоминания станций по частоте, чтобы пополнять `gazetteer.yaml`.
- `tests/` — pytest на чистых функциях пайплайна с фикстурами из реальных обезличенных сообщений.

## Модель данных

`FuelReport` — **append-only лог**, не перезаписываемая «текущая» запись. Несколько независимых сообщений про одну и ту же АЗС — подтверждение, а не дубликат (дедуп — только против повторной доставки Long Poll, через `ProcessedMessage`). «Текущий статус» и «свежесть» считаются на лету при запросе (последний отчёт по station+марка + возраст записи), а не фоновой задачей. Если два недавних отчёта по одной АЗС противоречат друг другу — это явно отражается в ответе, а не тихо разрешается в одну сторону.

Идентификация станции — по курируемому `gazetteer.yaml`, а не по чистому свободному тексту: у той же АЗС может быть несколько названий/опечаток в переписке, а свободный текст без справочника даёт нестабильные или ошибочные совпадения. Нераспознанные упоминания копятся в `unresolved_mention` для ручного разбора — станции не создаются автоматически из текста.

На реальных сообщениях чата подтвердилось: один и тот же бренд (например, «Роснефть»/«РН» — 4 точки, «Татнефть» — 3) может обозначать несколько разных точек в городе, а несколько разных брендов (Татнефть/Лукойл/Опти) стоят на одной и той же улице. Поэтому `gazetteer.yaml` хранит для каждой станции `brand_aliases` и `location_aliases` отдельно, а резолвер (`pipeline/resolve_station.py`) матчит их независимо: бренд с одной точкой резолвится сразу, бренд с несколькими — только если в тексте есть ещё и её локация. Голое упоминание бренда без уточнения адреса намеренно не резолвится ни в одну точку и уходит в `unresolved_mention`. Отдельный запасной путь — если бренд в тексте вообще не упомянут (например «заправился на суоярвском»), резолвер пробует найти станцию по одной лишь локации, но только если этот алиас уникален по всему газетиру (не повторяется у другой станции).

Известное ограничение MVP: пайплайн не отслеживает цепочки ответов (reply/thread) в беседе. Короткое уточнение вроде «Лесной 79» или «У суоярвского или другая?», отправленное отдельным сообщением в ответ на чужой отчёт, обрабатывается изолированно, без контекста родительского сообщения — иногда из-за этого теряется уточнение адреса или марки. Осознанно не реализовано в MVP; если станет заметной проблемой, можно добавить связывание через `reply_message`/`fwd_messages` в событии VK.

## Триггеры ответов

Оба режима, флаг `AUTO_REPLY_ON_QUESTION`:
- Упоминание/реплай боту — всегда работает.
- Автоответ на распознанный вопрос по теме — включается флагом (по умолчанию выключен, пока не проверена точность `extract.py` на реальном потоке сообщений).

Независимо от режима: дебаунс между сообщениями бота (`MIN_REPLY_GAP_SECONDS`), фильтр собственных сообщений, потолок ответов/минуту как страховка от флуда.

**Важный нюанс vkbottle**: разбор markup-упоминаний (`message.is_mentioned`, `message.mention`) по умолчанию выключен на уровне `ABCMessageView.replace_mention = False` — без явного `bot.labeler.message_view.replace_mention = True` в `bot.py` упоминания бота никогда не распознаются (тихо, без ошибки). Нашли это только на живом тесте.

**Реплай на чужой вопрос**: если сообщение адресовано боту (упоминание), но своего текста после вырезания упоминания не осталось — частый способ адресовать существующий вопрос («тегнуть бота реплаем на чужое сообщение»). В этом случае бот берёт текст из `message.reply_message` и отвечает по нему, ничего повторно не записывая в БД (это не новый отчёт).

**Известное ограничение rule-based резолвера**: матчит бренд по точному стему (`газпром\w*` и т.п.) — опечатка в самом бренде (например «газпропе» вместо «газпроме») ломает резолв, в отличие от опечаток в названиях локаций, для которых уже добавлены конкретные алиасы-варианты. Пока чиним точечно по мере обнаружения, общий fuzzy-matching сознательно не возвращали (см. Этап 2). Это ровно тот класс ошибок, для которого добавлен LLM-путь — см. ниже.

## LLM-анализ (опционально, флаг `LLM_ENABLED`)

Классификацию+извлечение+резолв станции можно передать бесплатному LLM (Groq, `llama-3.3-70b-versatile`) вместо `extract.py`/`resolve_station.py`. Вызывается на каждом сообщении, прошедшем `is_on_topic()`. При любом сбое (лимит/таймаут/сетевая ошибка/невалидный ответ) — прозрачный откат на rule-based; сам rule-based код при этом не удаляется и не меняется, LLM — альтернативная реализация той же функции `_analyze()` в `pipeline/pipeline.py`.

Извлечение сделано через **tool calling** (форсированный вызов функции `record_analysis` с JSON Schema), а не свободный `response_format=json_object` — Llama через Groq надёжнее соблюдает форму именно так. Ответ всё равно валидируется перед использованием (`llm/client.py:_parse_arguments`) — неизвестные типы/статусы марок молча отбрасываются, а не ломают весь разбор; это прямое следствие предупреждения самой библиотеки Groq: модель «does not always generate valid JSON, and may hallucinate parameters not defined by your function schema».

**Живая проверка** (`python -m scripts.compare_llm_vs_rules`, сравнение на тех же реальных сообщениях, что и `tests/fixtures.py`) показала ~77% полного совпадения с rule-based. Расхождения:
- Формулировки `queue_note` иногда отличаются косметически (оба варианта верны).
- LLM **лучше** rule-based: не путает «92 нет очереди» (это про очередь, марка available) при определённых формулировках до правки промпта; распознаёт станцию по алиасу без указания бренда за счёт того, что промпт теперь включает полный список алиасов (было упущено в первой версии промпта — нашли и починили тем же живым сравнением); делает разумные выводы из контекста («в гордом одиночестве» → скорее всего без очереди).
- LLM **хуже** rule-based в паре случаев: спутала составной вопрос («Есть ещё 95... и нет ли перерыва?») с отчётом; один раз неверно определила статус марки при неоднозначном порядке слов (промпт поправлен явным примером, повторно не воспроизвелось).
- LLM иногда извлекает факт, для которого в текущей схеме просто нет места — например «в очереди много свободного места» резолвится в правильную станцию с `queue_note`, но без марки топлива, а `pipeline.py` пишет в `fuel_report` только при непустом `reports` — такая находка молча пропадает. Известное ограничение схемы, не баг конкретно LLM-пути.
- Один пограничный случай (бренд с одной точкой в газетире, но упомянутый рядом с адресом другой, не своей, локации) — LLM осторожно вернула `null`, rule-based увереннее (но в этом случае правильнее) резолвнула по уникальности бренda. Оба поведения защитимы, выбор неочевиден.

Вывод: LLM полезнее там же, где ожидалось (опечатки, нестандартные формулировки), но не безошибочна и не строго превосходит rule-based по всем пунктам — поэтому откат на rule-based при сбое, а не полная замена, и почему `LLM_ENABLED=false` по умолчанию до накопления большего числа живых наблюдений.

## Деплой

Docker-контейнер с одним Long Poll-воркером на небольшом VPS — публичный HTTPS не нужен благодаря Long Poll. `docker-compose`, volume под SQLite-файл и `gazetteer.yaml`, секреты через `.env`.

## Возможное развитие (не в MVP)

- Включить `AUTO_REPLY_ON_QUESTION` по умолчанию после проверки точности на реальных данных.
- Включить `LLM_ENABLED` по умолчанию после накопления живых наблюдений (см. «LLM-анализ» выше).
- Схема `FuelReport` не поддерживает факты про очередь без привязки к марке топлива — LLM-путь такие уже находит, rule-based путь до них просто не доходит (нет grade-токена). Стоит обсудить, добавлять ли такой тип факта.
- OCR/анализ фото ценников и очередей через vision-модель (Groq/Llama тоже умеют мультимодальный ввод — можно тем же путём).
- Миграция Long Poll → Callback API при расширении на несколько бесед/городов; тогда же пересмотреть SQLite в пользу БД с нормальной поддержкой многопроцессной записи.
