# Архитектура

## Пайплайн

```
Long Poll (vkbottle) → фильтр себя/дублей → склейка контекста
    (fwd_messages/reply_message — структурно, rule-based+LLM; предыдущее
     сообщение автора из in-memory кэша — только LLM) → pre-filter (тема?)
    → классификация+извлечение+резолв станции (LLM, если LLM_ENABLED и доступен; иначе/при сбое — rule-based)
        → отчёт: запись в БД (fuel_report append-only; station_break append-only, если есть сигнал о перерыве)
        → вопрос: выборка свежих фактов по маркам + последнего перерыва → рендер шаблона → (если триггер сработал) отправка ответа
```

Генерация текста ответа — всегда через `templates.py`, независимо от того, кто делал разбор (LLM или regex). Это единственная защита от галлюцинаций: бот физически не может «нафантазировать» несуществующую АЗС или статус — шаблон использует только то, что реально есть в базе.

## Компоненты

- `bot.py` — точка входа: инициализация `vkbottle.Bot`, запуск Long Poll.
- `config.py` — настройки из env: `VK_TOKEN`, `GROUP_ID`, `ADMIN_ID`, пороги свежести данных, `AUTO_REPLY_ON_QUESTION`, настройки debounce.
- `vk_handlers.py` — обработчик `message_new`: отсечение собственных сообщений бота (`from_id == -GROUP_ID`), проверка идемпотентности, склейка контекста (`_quoted_context_text` — текст `fwd_messages`/`reply_message`, один уровень без рекурсии; `_last_author_message` — короткоживущий in-memory кэш последнего сообщения автора, только для LLM-ветки), диспетчеризация в пайплайн, единая точка отправки ответов (debounce/rate-limit).
- `pipeline/prefilter.py` — быстрый keyword-фильтр по теме (бензин/азс/заправ-/очеред-/марки топлива/geo-вложение/фото).
- `pipeline/extract.py` — regex/keyword-извлечение марки топлива, статуса наличия, длины очереди, технического перерыва (`слив`/`отстой`/`перерыв`, время в формате «до HH:MM» или диапазон «HH-HH ч»); классификация отчёт/вопрос/нерелевантно. `break_info` — сигнал, независимый от `message_type` (может быть в отчёте, может подразумеваться и в вопросе, но для вопроса не заполняется — ответ про перерыв всегда строится из БД, не из текста вопроса). Rule-based путь и фолбэк для LLM-пути.
- `pipeline/facts.py` — дата-классы `StationFact`/`StationBreak`, которые видят и `qa.py`, и `templates.py`; общий `MOSCOW_TZ` для конвертации времени перерыва в локальное.
- `pipeline/resolve_station.py` — сопоставление упоминания с известной АЗС: матчинг «бренд + локация» по алиасам из газетира (см. «Модель данных»), иначе — запись в `unresolved_mention`. Rule-based путь и фолбэк для LLM-пути.
- `pipeline/pipeline.py` — `_analyze()`: если `LLM_ENABLED` — сначала `llm.client.analyze()`, при `None` (сбой/лимит/невалидный ответ) — `extract()`+`resolve_station()` без изменений. См. «LLM-анализ» ниже.
- `llm/client.py` — тонкий диспетчер по `config.LLM_PROVIDER`: лениво импортирует `llm/groq_client.py`, `llm/gemini_client.py` или `llm/mistral_client.py`, прогоняет сырой ответ через общий `_parse_arguments`. Реэкспортирует `LLMAnalysis`/`_parse_arguments` из `llm/schema.py` — единственная точка входа для `pipeline.py` и `scripts/compare_llm_vs_rules.py`.
- `llm/schema.py` — провайдер-агностичное ядро: поля/enum'ы схемы разбора (`PARAMETERS_SCHEMA`), `LLMAnalysis`, `_parse_arguments()` (валидация сырого ответа модели, включая проверку `station_id` на членство в газетире через `resolve_station.is_known_station`).
- `llm/groq_client.py` / `llm/gemini_client.py` — обёртки над Groq (`groq` SDK) и Gemini (`google-genai` SDK) соответственно: классификация+извлечение+резолв станции одним вызовом (forced tool/function calling), каждая отдаёт `raw_analyze(text) -> dict | None`, `None` при любом сбое. `gemini_client.py` дополнительно конвертирует `PARAMETERS_SCHEMA` в нативный диалект Gemini (`_to_gemini_schema` — nullable как отдельный флаг, не union-тип).
- `llm/prompts.py` — системный промпт: правила разбора, полный газетир (включая алиасы) как контекст, few-shot примеры. Провайдер-агностичен (чистый текст), исторически настраивался и валидировался в первую очередь под Groq — но живой тест 2026-08-10 (Этапы 9-12 и последующие правки) прошёл на Gemini, так что оба провайдера теперь имеют живую (не только офлайн-сравнение) проверку — см. «LLM-анализ» ниже.
- `pipeline/qa.py` — для вопроса: выборка последних фактов по станции/марке, расчёт свежести (tier: свежо/устарело/старо) на момент запроса, плюс последняя запись о техническом перерыве по станции (`_latest_break` — без окна активности, всегда самая свежая запись), рендер ответа через шаблоны.
- `templates.py` — компактный формат ответа (с Этапа 8): марки с одинаковым статусом сгруппированы в одну строку, один абсолютный timestamp в заголовке вместо возраста на каждой строке; строка про технический перерыв — сразу после заголовка, вместе с фактами по маркам, а не вместо них.
- `db/schema.py`, `db/repo.py` — SQLite: `fuel_report`, `station_break`, `unresolved_mention`, `processed_message`. Идентичность станций в БД не хранится — единственный источник правды по станциям это `gazetteer.yaml` (см. ниже), в БД станция — это просто `station_id` (строка-ключ из газетира).
- `gazetteer.yaml` — вручную поддерживаемый список известных АЗС (id, название, бренд, адрес, алиасы). Загружается в память при старте, отдельных таблиц `Station`/`StationAlias` в БД сознательно нет — дублировать источник правды незачем.
- `scripts/review_unresolved.py` — CLI: нераспознанные упоминания станций по частоте, чтобы пополнять `gazetteer.yaml`.
- `tests/` — pytest на чистых функциях пайплайна с фикстурами из реальных обезличенных сообщений.

## Модель данных

`FuelReport` — **append-only лог**, не перезаписываемая «текущая» запись. Несколько независимых сообщений про одну и ту же АЗС — подтверждение, а не дубликат (дедуп — только против повторной доставки Long Poll, через `ProcessedMessage`). «Текущий статус» и «свежесть» считаются на лету при запросе (последний отчёт по station+марка + возраст записи), а не фоновой задачей. Если два недавних отчёта по одной АЗС противоречат друг другу — это явно отражается в ответе, а не тихо разрешается в одну сторону.

Идентификация станции — по курируемому `gazetteer.yaml`, а не по чистому свободному тексту: у той же АЗС может быть несколько названий/опечаток в переписке, а свободный текст без справочника даёт нестабильные или ошибочные совпадения. Нераспознанные упоминания копятся в `unresolved_mention` для ручного разбора — станции не создаются автоматически из текста.

На реальных сообщениях чата подтвердилось: один и тот же бренд (например, «Роснефть»/«РН» — 5 точек, «Татнефть» — 4, «Лукойл» — 5, «Опти» — 2) может обозначать несколько разных точек в городе, а несколько разных брендов (Татнефть/Лукойл/Опти) стоят на одной и той же улице. Это касается даже брендов, которые долго были в газетире единственной точкой (Опти) — как только появляется вторая, голое упоминание бренда без адреса перестаёт резолвиться однозначно, это не баг, а прямое следствие правила «бренд с одной точкой резолвится сразу, с несколькими — нужна ещё и локация». Поэтому `gazetteer.yaml` хранит для каждой станции `brand_aliases` и `location_aliases` отдельно, а резолвер (`pipeline/resolve_station.py`) матчит их независимо: бренд с одной точкой резолвится сразу, бренд с несколькими — только если в тексте есть ещё и её локация. Голое упоминание бренда без уточнения адреса намеренно не резолвится ни в одну точку и уходит в `unresolved_mention`. Отдельный запасной путь — если бренд в тексте вообще не упомянут (например «заправился на суоярвском»), резолвер пробует найти станцию по одной лишь локации, но только если этот алиас уникален по всему газетиру (не повторяется у другой станции).

~~Известное ограничение MVP: пайплайн не отслеживает цепочки ответов (reply/thread) в беседе.~~ — **решено 2026-08-10 (Этапы 9-10)**: `reply_message`/`fwd_messages` подклеиваются к тексту перед анализом (один уровень, без рекурсии в их собственные reply/fwd) — короткое уточнение вроде «а очередь есть?» реплаем на чужой отчёт теперь резолвит станцию из цитаты. Отдельно, только для LLM-пути — короткоживущий (TTL 120 сек) in-memory кэш последнего сообщения того же автора в том же чате, для случаев без явной VK reply-связи («95 есть на Газпроме?» → следом «большая очередь?»). Гвард в `pipeline.py` не даёт факту из чужой цитаты записаться в БД, если собственный текст автора сам по себе ничего не сообщает (например «спасибо»-реплай) — иначе случайная реплика искусственно освежила бы старый факт под новым timestamp.

`StationBreak` (`station_break`) — **тоже append-only лог**, отдельный от `FuelReport`: технический перерыв («слив бензовоза», «отстой топлива», «тех перерыв до HH:MM») — факт про станцию целиком (все марки), а не про одну марку. `until` парсится в ISO UTC из «до HH:MM»/диапазона «HH-HH ч», местное время — фиксированный offset `+3` (Москва/Петрозаводск), без учёта переноса через полночь (не наблюдалось в реальных сообщениях). `qa.py::_latest_break` — по прямому решению пользователя, **без окна активности**: возвращается последняя запись по станции всегда, с возрастом, без автоматической деактивации по таймауту — перерыв, о завершении которого никто не написал, продолжает упоминаться сколь угодно долго с растущим «сообщили N назад». Ответ показывает перерыв и факты по маркам **вместе**, одно не подменяет другое.

## Триггеры ответов

Оба режима, флаг `AUTO_REPLY_ON_QUESTION`:
- Упоминание/реплай боту — всегда работает.
- Автоответ на распознанный вопрос по теме — включается флагом (по умолчанию выключен, пока не проверена точность `extract.py` на реальном потоке сообщений).

Независимо от режима: дебаунс между сообщениями бота (`MIN_REPLY_GAP_SECONDS`), фильтр собственных сообщений, потолок ответов/минуту как страховка от флуда.

**Важный нюанс vkbottle**: разбор markup-упоминаний (`message.is_mentioned`, `message.mention`) по умолчанию выключен на уровне `ABCMessageView.replace_mention = False` — без явного `bot.labeler.message_view.replace_mention = True` в `bot.py` упоминания бота никогда не распознаются (тихо, без ошибки). Нашли это только на живом тесте.

**Реплай на чужой вопрос**: раньше был отдельный узкий механизм (`_answer_for_parent_message` — только пустой свой текст + упоминание + `reply_message`, только rule-based). С Этапа 9 убран — этот случай покрывается общей склейкой контекста (см. «Модель данных»): пустой свой текст + реплай даёт `combined_text` = только текст цитаты, идёт через обычный пайплайн (в том числе LLM, если включён). Побочный эффект обобщения: реплай без текста на чужой **отчёт** (не только на вопрос) теперь тоже может залогировать факт, а не молчать, как раньше.

**Известное ограничение rule-based резолвера**: матчит бренд по точному стему (`газпром\w*` и т.п.) — опечатка в самом бренде (например «газпропе» вместо «газпроме») ломает резолв, в отличие от опечаток в названиях локаций, для которых уже добавлены конкретные алиасы-варианты. Пока чиним точечно по мере обнаружения, общий fuzzy-matching сознательно не возвращали (см. Этап 2). Это ровно тот класс ошибок, для которого добавлен LLM-путь — см. ниже.

**Молчание вместо шаблонного «не знаю»** (с 2026-08-10, по прямому запросу пользователя): если станция не распознана, или распознана, но по ней вообще нет отчётов в БД, `pipeline/qa.py::answer_question` возвращает `None`, и `vk_handlers.py` просто не отправляет ответ — раньше в обоих случаях бот писал в чат шаблонное «не понял, о какой АЗС» / «нет данных». Единственный ответ, который бот теперь пишет — содержательный (есть хотя бы один факт по станции). `templates.render_unknown_station` за ненадобностью удалена.

**Тег адресата**: при отправке ответа `vk_handlers.py::_mention_tag` подставляет `[id<from_id>|Имя]` в начало текста — имя запрашивается через `users.get` на лету (без кеша). Если `from_id` не пользователь (например, сообщение от другого сообщества в этой же беседе), тег пропускается, ответ уходит без него.

## LLM-анализ (опционально, флаг `LLM_ENABLED`, провайдер — `LLM_PROVIDER`)

Классификацию+извлечение+резолв станции можно передать бесплатному LLM (`LLM_PROVIDER=groq`, `llama-3.3-70b-versatile`, по умолчанию; или `LLM_PROVIDER=gemini`, `gemini-flash-lite-latest`) вместо `extract.py`/`resolve_station.py`. Вызывается на каждом сообщении, прошедшем `is_on_topic()`. При любом сбое (лимит/таймаут/сетевая ошибка/невалидный ответ) — прозрачный откат на rule-based; сам rule-based код при этом не удаляется и не меняется, LLM — альтернативная реализация той же функции `_analyze()` в `pipeline/pipeline.py`.

Извлечение сделано через **tool calling** (форсированный вызов функции `record_analysis` с JSON Schema), а не свободный `response_format=json_object` — Llama через Groq надёжнее соблюдает форму именно так. Ответ всё равно валидируется перед использованием (`llm/client.py:_parse_arguments`) — неизвестные типы/статусы марок молча отбрасываются, а не ломают весь разбор; это прямое следствие предупреждения самой библиотеки Groq: модель «does not always generate valid JSON, and may hallucinate parameters not defined by your function schema».

**Живая проверка** (`python -m scripts.compare_llm_vs_rules`, сравнение на тех же реальных сообщениях, что и `tests/fixtures.py`) показала ~77% полного совпадения с rule-based. Расхождения:
- Формулировки `queue_note` иногда отличаются косметически (оба варианта верны).
- LLM **лучше** rule-based: не путает «92 нет очереди» (это про очередь, марка available) при определённых формулировках до правки промпта; распознаёт станцию по алиасу без указания бренда за счёт того, что промпт теперь включает полный список алиасов (было упущено в первой версии промпта — нашли и починили тем же живым сравнением); делает разумные выводы из контекста («в гордом одиночестве» → скорее всего без очереди).
- LLM **хуже** rule-based в паре случаев: спутала составной вопрос («Есть ещё 95... и нет ли перерыва?») с отчётом; один раз неверно определила статус марки при неоднозначном порядке слов (промпт поправлен явным примером, повторно не воспроизвелось).
- LLM иногда извлекает факт, для которого в текущей схеме просто нет места — например «в очереди много свободного места» резолвится в правильную станцию с `queue_note`, но без марки топлива, а `pipeline.py` пишет в `fuel_report` только при непустом `reports` — такая находка молча пропадает. Известное ограничение схемы, не баг конкретно LLM-пути.
- Один пограничный случай (бренд с одной точкой в газетире, но упомянутый рядом с адресом другой, не своей, локации) — LLM осторожно вернула `null`, rule-based увереннее (но в этом случае правильнее) резолвнула по уникальности бренda. Оба поведения защитимы, выбор неочевиден.

Вывод по офлайн-сравнению: LLM полезнее там же, где ожидалось (опечатки, нестандартные формулировки), но не безошибочна и не строго превосходит rule-based по всем пунктам — поэтому откат на rule-based при сбое, а не полная замена.

### Включение в проде и живой тест (2026-08-10)

`LLM_ENABLED=true` включён для живого теста в обеих реальных беседах. Перед включением аудит кода нашёл и закрыл реальную дыру: `_parse_arguments` проверял только тип/непустоту `station_id`, не членство в газетире — придуманный LLM id уходил либо в необработанный `KeyError` в `get_station_name` (вопрос о станции), либо тихим мусором в `fuel_report` (отчёт), и то и другое обходило существующий механизм отката, потому что формально не было «сбоем». Добавлена `resolve_station.is_known_station()`, используется в `_parse_arguments` — неизвестный id теперь трактуется как `None`, ровно как у rule-based. Заодно добавлено логирование `path=llm`/`path=rule_based reason=llm_fallback` в `pipeline.py` — раньше нигде не было видно, какой путь реально обработал сообщение.

**Живой тест подтвердил ту же природу риска ещё раз, уже на реальных сообщениях, и хуже, чем ожидалось**: на реальном сообщении «слив топлива... ГН напротив РБ 92,95, ДТ...» LLM в 4 из 6 идентичных повторных вызовов **придумал факт «АИ-100 недоступен»**, которого в тексте не было вообще ни в каком виде. Это не сбой (нет исключения/таймаута) — ответ формально валиден, значит существующий откат не срабатывает, а `is_known_station` эту категорию ошибки не ловит (сфабрикован не id, а `reports`-запись). Отдельно, на другом реальном сообщении («Татнефть... 7 машин», без указания локации при 4 точках бренда) LLM уверенно выбрал `tatneft_shuyskoe`, хотя текст не давал для этого никаких оснований — rule-based в той же ситуации корректно вернул бы `None`. В третьем похожем случае (сообщение с тремя разными брендами сразу) LLM, наоборот, правильно вернул `station_id=None`, не угадывая — то есть поведение на неоднозначности **не детерминировано**, кода, который бы гарантированно ловил именно такие «уверенные, но безосновательные» ответы, сейчас нет. Пользователь решил осознанно продолжать жить с этим риском (см. PROGRESS.md, живой тест) — не фиксили точечно, чтобы не гнаться за одним симптомом; при возврате к этой теме почитать `queue_note` (см. следующий абзац) — тоже кандидат на переработку валидации.

**`queue_note` — единственное поле, которое LLM пишет в чат почти без валидации**: `_parse_arguments` проверяет только, что это непустая строка (в отличие от rule-based, где `queue_note` жёстко ограничен фиксированными regex-паттернами) — свободный текст от модели долетает до `templates.py` и в ответ пользователю почти как есть. За время живого теста ничего одиозного не пришло, но это структурно единственная щель, где модель может написать в публичный чат произвольный текст.

**Экономика бесплатного тарифа Groq**: дневной лимит (100k токенов, `llama-3.3-70b-versatile`, на организацию — привязан к аккаунту, не к ключу) исчерпался дважды за первый час живого теста при обычной активности чата. Восстановление ведёт себя не как разовый сброс раз в сутки, а скорее как скользящее окно — короткие окна доступности, снова упирается в потолок в течение нескольких минут. Системный промпт (полный газетир + few-shot) отправляется целиком на **каждый** вызов и, видимо, основная статья расхода токенов — не оптимизировали сегодня, кандидат на сокращение, если понадобится растянуть дневной лимит на большее число сообщений.

Вывод на сегодня: `LLM_ENABLED=true` остаётся включённым осознанно, несмотря на подтверждённый риск галлюцинации фактов — решение пользователя после того, как увидел конкретные цифры (4/6 на одном сообщении), не гипотетически. Если это станет проблемой на практике, следующий шаг — не «выключить», а разобраться, почему модель фабрикует записи в `reports`, когда её не просят (промпт? температура? формат tool call?).

### Второй провайдер: Gemini (2026-08-10)

Причина: дневной бюджет Groq (100k токенов) исчерпывается примерно за час активного чата. `LLM_PROVIDER=gemini` (`llm/gemini_client.py`, SDK `google-genai`, forced function calling через `types.ToolConfig(mode="ANY")`) — та же схема разбора (`llm/schema.py`), тот же промпт (`llm/prompts.py`), другой транспорт.

**Лимит другой природы, не лучше и не хуже, а просто другой риск.** У Groq — большой дневной бюджет токенов, кончается постепенно за час-полтора активного дня. У бесплатного Gemini лимит по запросам **в минуту**: 5 RPM у модели, на которую резолвится алиас `gemini-flash-latest` (сейчас это `gemini-3.6-flash`); ~8-9 RPM у `gemini-flash-lite-latest` — на неё и переключили дефолт. Для тихого сбора (анализируется каждое тематическое сообщение, не только адресованные боту) это значит: при всплеске активности (несколько человек пишут в течение одной минуты) фолбэк на rule-based может срабатывать чаще всего именно тогда, когда сообщений больше всего — не проверяли живьём в реальном чате, только синтетической нагрузкой на API напрямую.

**Промпт настроен под Groq, на Gemini не переносится один в один — но три найденных расхождения починены в тот же день.** Изначально на том же наборе сравнения, что и офлайн-проверка Groq (`compare_llm_vs_rules.py`): 12 чистых совпадений из 15 (прежде чем упёрлись в RPM), 3 реальных расхождения — сообщение про Янишполе («появился 95-й... заправилась за 12 минут») целиком ушло в `irrelevant`, потеряв факт; «92 нет очереди на остальных колонках» распознано как «92 недоступен» (та самая ловушка порядка слов, для которой в промпте есть явное правило — сработавшее у Groq, не у Gemini); резолв станции по одной локации без бренда («У суоярвского или другая?») — не сработал, хотя это тот самый кейс, специально чинившийся в промпте для Groq (см. выше, «Живая проверка», Этап 4). Все три уточнены в `llm/prompts.py` (декларация правил + по новому few-shot примеру на каждый) и переподтверждены живьём (3/3 на каждый). Побочный эффект: правило про резолв по уникальной локации без бренда сначала перебивало явно названный бренд («опти на суоярвском...» стало резолвиться в чужую станцию по совпадению локации) — пойман и закрыт в той же правке явным уточнением приоритета бренда. Полное сравнение выросло до 15/16. Промпт общий с Groq — эти правки НЕ переподтверждены живьём на Groq (квота ещё не обновилась на момент правки); они по характеру аддитивные/уточняющие, не сужают уже работавшие правила, но это рассуждение, а не факт — стоит перепроверить `compare_llm_vs_rules.py` под `LLM_PROVIDER=groq`, когда квота освободится.

**На специфический риск галлюцинации фактов — обнадёживает, но выборка маленькая.** Те же два сообщения, что вскрыли проблемы у Groq (см. выше): «слив топлива... ГН напротив РБ 92,95,ДТ...» — 0 из 3 повторов с придуманной маркой (у Groq 4 из 6), причём станция резолвнулась осмысленнее — в `gazprom` (туда, откуда реально цифры), а не в Роснефть по совпадению алиаса «рб», как у Groq и rule-based. «Татнефть... 7 машин» без локации — `station_id=None` во всех 3 повторах, ни разу не угадал наугад (у Groq — уверенно, но безосновательно `tatneft_shuyskoe`). Три повтора на два сообщения — не статистика, только направление; относиться как к первому наблюдению, не как к доказанному свойству модели.

### Третий провайдер: Mistral (2026-08-13)

Причина: на живом деплое (library-vps, см. «Деплой» ниже) дневной бюджет Groq (100k токенов) реально исчерпался в первый же вечер и держал бот на rule-based-фолбэке around 2 часа подряд — тот же риск, что и раньше, но теперь на реальном постоянном трафике, не разовом тесте. `LLM_PROVIDER=mistral` (`llm/mistral_client.py`, SDK `mistralai`) — та же схема разбора (`llm/schema.py`), тот же промпт (`llm/prompts.py`), третий транспорт.

**Лимит — снова другой природы, и структурно лучше подходит именно этому боту.** У Mistral лимиты по токенам/запросам **в минуту** (как у Gemini), не по дням (как у Groq) — то есть тот конкретный отказ, который случился с Groq (жди 40+ минут, пока не освободится дневной бюджет), тут структурно не воспроизводится. Организационные лимиты проверены пользователем напрямую в `admin.mistral.ai`: `ministral-8b-2512` — 625 000 TPM / 3.13 RPS, выбрана как баланс между запасом по токенам и, что важнее для чата со всплесками сообщений, достаточным RPS (сравнимые модели `mistral-small-2603` дают всего 0.83 RPS — заметно теснее для пары сообщений подряд за несколько секунд, что в реальном трафике этого чата обычное дело, см. живой лог 2026-08-13).

**Та же ловушка «-latest», что и с Gemini, поймана заранее, не на живом сбое.** На странице лимитов `mistral-medium-latest` резолвится в модель с 25 000 TPM — заметно хуже датированных `mistral-medium-2505`/`2508` (356-375k TPM). Ровно та же природа риска, что уже стоила времени на Gemini (`gemini-flash-latest` резолвился в модель с 5 RPM вместо `gemini-flash-lite-latest` с 8-9) — решили не наступать повторно и сразу закрепили `MISTRAL_MODEL=ministral-8b-2512` датированной версией, не алиасом.

**SDK — тоже сгенерирован Speakeasy** (та же кодогенерация, что и у `groq`), конструктор `Mistral(client=...)` принимает произвольный httpx-совместимый клиент — ровно тот же приём `httpx.Client(proxy=AI_PROXY_URL)`, что уже работал для Groq (см. «Деплой», AI-провайдер из заблокированной страны). **Прокси в данном случае, похоже, не обязателен**: прямой вызов `api.mistral.ai` с library-vps (без туннеля) дал `401`, не `403` — в отличие от Groq/Gemini, Mistral (французская компания, не под американскими экспортными ограничениями) Россию, по всей видимости, не блокирует. Обвязка через `AI_PROXY_URL` всё равно добавлена — симметрично, дёшево, и на случай, если это изменится.

**Схема запроса не требует конвертации**, в отличие от Gemini: tool calling у Mistral по форме совместим с Groq/OpenAI (`tools=[{"type": "function", "function": {...}}]`, `tool_choice={"type": "function", "function": {"name": ...}}` форсирует нужный вызов) — `PARAMETERS_SCHEMA` из `llm/schema.py` используется как есть, без аналога `_to_gemini_schema`. Единственная особенность, не встречавшаяся у Groq: SDK типизирует `tool_calls[0].function.arguments` как `Union[dict, str]` (не всегда строка) — `llm/mistral_client.py` обрабатывает оба случая; какой вариант реально приходит от модели чаще, живой проверкой на объёме пока не подтверждено, был один ручной тест (см. ниже).

**Живая проверка — пока один ручной вызов, не `compare_llm_vs_rules.py`.** Вопрос «РН на Лыжной есть 95? Очередь большая?» → верно `question`/`rosneft_lyzhnaya`/`question_grades=["95"]` с первой попытки. Этого достаточно, чтобы подтвердить, что интеграция в принципе работает (ключ верный, модель верная, forced tool call проходит), но не достаточно для содержательного сравнения с rule-based/Groq/Gemini по типу того, что есть у остальных двух провайдеров — стоит прогнать `compare_llm_vs_rules.py` под `LLM_PROVIDER=mistral` на тех же фикстурах, когда будет время.

## Возможное развитие (не в MVP)

- ~~На самом деле бесед с инфой/вопросами про бензин две, бот подключён только к одной~~ — **решено 2026-08-10**: пользователь подключил бота во вторую беседу и явно подтвердил, что факты нужно объединять между беседами (один город, одни и те же АЗС). Код уже был к этому готов без изменений — `pipeline/qa.py`/`_latest_facts` никогда не фильтровали по `peer_id`, это и есть текущее поведение. Если когда-нибудь понадобится разделение — фильтр по `peer_id` в `_latest_facts`.
- Включить `AUTO_REPLY_ON_QUESTION` по умолчанию после проверки точности на реальных данных.
- ~~Включить `LLM_ENABLED` по умолчанию~~ — **включён 2026-08-10** для живого теста в проде (см. «LLM-анализ» выше, раздел «Включение в проде и живой тест»). Открыто: подтверждённая галлюцинация фактов в `reports` (не только «нет места в схеме», а прямая фабрикация), пока живём с риском осознанно.
- Схема `FuelReport` не поддерживает факты про очередь без привязки к марке топлива — LLM-путь такие уже находит, rule-based путь до них просто не доходит (нет grade-токена). Стоит обсудить, добавлять ли такой тип факта.
- Архитектурное ограничение, подтверждённое несколько раз в живом тесте 2026-08-10 (включая повторно, уже после Этапов 9-12, на реальном сообщении «Мимо татнефти... Через полчаса проезжал мимо РН, там очередь машин 40» — обе станции безадресные и неоднозначные, сообщение целиком ушло в `irrelevant`, потеряв обе очереди): и LLM, и rule-based поддерживают только один `station_id` на сообщение. Затронуло бы и вопросы, и отчёты, и (с Этапа 11) технические перерывы. Не спроектировано, как чинить — потребует менять форму `ExtractResult`/tool schema на список станций, а не одну.
- Живой тест 2026-08-10 (после Этапов 9-12) нашёл и починил в тот же день: (а) общий вопрос про перерывы без марки топлива и без конкретной станции классифицировался как `irrelevant` вместо `question` — верхнеуровневые определения категорий в промпте остались заточены под «топливо/очередь» и не обновились вместе с добавлением `break_info`, поправлено правилами+примером; (б) лог писал только сырой `message.text`, не реально проанализированный (обогащённый цитатой/контекстом автора) текст — не давало продиагностировать, откуда взялась неожиданная классификация; поправлено, теперь логируются `own_text`/`quoted`/`prev_msg` раздельно.
- Найдено живьём, не починено: короткие реплики в диалоге («Есть.», «это на силикатном?» — однословное подтверждение или короткий уточняющий вопрос) иногда классифицируются как `question` при том, что процитированный/предыдущий контекст содержит «?» — модель может путать «это вопрос где-то в контексте» с «текущее сообщение — вопрос». Эффект пока мягкий (гвард в `pipeline.py` не даёт это записать как отчёт; в худшем случае лишний ответ). Два случая за один живой прогон — не закономерность, нужно больше наблюдений перед правкой промпта.
- Найдено живьём, не починено: словарь ключевых слов перерыва (`слив`/`отстой`/`перерыв` — и в `extract.py`, и в промпте) не покрывает синонимичные обороты вроде «закрывается»/«были закрыты» — реальное сообщение с описанием паттерна закрытий по времени было потеряно (rule-based дало `irrelevant`, LLM в контексте чата тоже). В изоляции (без обогащения контекстом) тот же текст на Gemini разбирается верно как `report` — то есть проблема именно в словаре, не в базовой способности модели. Стоит расширить `_BREAK_KIND_WORDS` и промпт по мере накопления реальных формулировок, как это уже делается для алиасов газетира.
- Промпт живо провалидирован на Gemini расширенно (весь живой тест 2026-08-10 шёл на `LLM_PROVIDER=gemini`, включая новые правила Этапа 12 и живой фикс для (а) выше). На Groq новые правила Этапа 12 и живой фикс подтверждены лишь частично — дневной токен-бюджет дважды заканчивался прямо во время проверки; нужно перепрогнать `compare_llm_vs_rules.py` под `LLM_PROVIDER=groq`, когда лимит освободится.
- Сократить системный промпт LLM (`llm/prompts.py`) — сейчас полный газетир+few-shot едет на каждый вызов и, похоже, основная статья расхода дневного лимита Groq (см. «LLM-анализ»).
- Префильтр (`pipeline/prefilter.py`) не знает про локации из газетира вообще, кроме одного точечного исключения — «вилга» (единственная АЗС там, добавлено 2026-08-10). Голые упоминания других локаций без бренда/цифры/др. ключевых слов по-прежнему проходят мимо анализа. Не расширяли на весь газетир осознанно — часть новых алиасов локаций (например «магнит», «правда») это обычные бытовые слова, широкое включение утроило бы ложные срабатывания и зря жгло бы лимит LLM.
- OCR/анализ фото ценников и очередей через vision-модель (Groq/Llama тоже умеют мультимодальный ввод — можно тем же путём).
- Миграция Long Poll → Callback API при расширении на несколько бесед/городов; тогда же пересмотреть SQLite в пользу БД с нормальной поддержкой многопроцессной записи.
