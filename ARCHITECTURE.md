# Архитектура

## Пайплайн

```
Long Poll (vkbottle) → фильтр себя/дублей → pre-filter (тема?)
    → rule-based классификация (отчёт / вопрос / нерелевантно)
        → отчёт: извлечение полей → резолв АЗС по газетиру → запись в БД (append-only)
        → вопрос: резолв АЗС/района → выборка свежих фактов → рендер шаблона → (если триггер сработал) отправка ответа
```

Без LLM: классификация, извлечение полей и генерация ответов — на regex/ключевых словах и шаблонах, а не через внешний LLM API. Плюс: бот не может «нафантазировать» несуществующую АЗС или статус — шаблон использует только то, что реально есть в базе. Минус: хуже справляется с нестандартными формулировками, требует ручной донастройки правил по реальным сообщениям чата.

## Компоненты

- `bot.py` — точка входа: инициализация `vkbottle.Bot`, запуск Long Poll.
- `config.py` — настройки из env: `VK_TOKEN`, `GROUP_ID`, `ADMIN_ID`, пороги свежести данных, `AUTO_REPLY_ON_QUESTION`, настройки debounce.
- `vk_handlers.py` — обработчик `message_new`: отсечение собственных сообщений бота (`from_id == -GROUP_ID`), проверка идемпотентности, диспетчеризация в пайплайн, единая точка отправки ответов (debounce/rate-limit).
- `pipeline/prefilter.py` — быстрый keyword-фильтр по теме (бензин/азс/заправ-/очеред-/марки топлива/geo-вложение/фото).
- `pipeline/extract.py` — regex/keyword-извлечение марки топлива, статуса наличия, длины очереди; классификация отчёт/вопрос/нерелевантно.
- `pipeline/resolve_station.py` — сопоставление упоминания с известной АЗС: точное/fuzzy совпадение по названию и алиасам (`rapidfuzz`), приоритет geo-вложению, иначе — запись в `UnresolvedMention`.
- `pipeline/qa.py` — для вопроса: выборка последних фактов по станции/марке, расчёт свежести (tier: свежо/устарело/нет данных) на момент запроса, рендер ответа через шаблоны.
- `templates.py` — русские шаблоны ответов: свежие данные / устаревшие / нет данных / противоречивые данные / станция не распознана.
- `db/schema.py`, `db/repo.py` — SQLite: `Station`, `StationAlias`, `FuelReport`, `UnresolvedMention`, `ProcessedMessage`.
- `gazetteer.yaml` — вручную поддерживаемый список известных АЗС (название, бренд, адрес, алиасы, координаты).
- `scripts/review_unresolved.py` — CLI: нераспознанные упоминания станций по частоте, чтобы пополнять `gazetteer.yaml`.
- `tests/` — pytest на чистых функциях пайплайна с фикстурами из реальных обезличенных сообщений.

## Модель данных

`FuelReport` — **append-only лог**, не перезаписываемая «текущая» запись. Несколько независимых сообщений про одну и ту же АЗС — подтверждение, а не дубликат (дедуп — только против повторной доставки Long Poll, через `ProcessedMessage`). «Текущий статус» и «свежесть» считаются на лету при запросе (последний отчёт по station+марка + возраст записи), а не фоновой задачей. Если два недавних отчёта по одной АЗС противоречат друг другу — это явно отражается в ответе, а не тихо разрешается в одну сторону.

Идентификация станции — по курируемому `gazetteer.yaml`, а не по чистому свободному тексту: у той же АЗС может быть несколько названий/опечаток в переписке, а свободный текст без справочника даёт нестабильные или ошибочные совпадения. Нераспознанные упоминания копятся в `UnresolvedMention` для ручного разбора — станции не создаются автоматически из текста.

## Триггеры ответов

Оба режима, флаг `AUTO_REPLY_ON_QUESTION`:
- Упоминание/реплай боту — всегда работает.
- Автоответ на распознанный вопрос по теме — включается флагом (по умолчанию выключен, пока не проверена точность `extract.py` на реальном потоке сообщений).

Независимо от режима: дебаунс между сообщениями бота, фильтр собственных сообщений, потолок ответов/минуту как страховка от флуда.

## Деплой

Docker-контейнер с одним Long Poll-воркером на небольшом VPS — публичный HTTPS не нужен благодаря Long Poll. `docker-compose`, volume под SQLite-файл и `gazetteer.yaml`, секреты через `.env`.

## Возможное развитие (не в MVP)

- Включить `AUTO_REPLY_ON_QUESTION` по умолчанию после проверки точности на реальных данных.
- Точечно подключить LLM (например, Claude API) именно в `extract.py`/`qa.py` как альтернативную реализацию тех же функций, если rule-based точности не хватит — остальной пайплайн (VK, БД, триггеры) переделывать не придётся.
- OCR/анализ фото ценников и очередей через vision-модель.
- Миграция Long Poll → Callback API при расширении на несколько бесед/городов; тогда же пересмотреть SQLite в пользу БД с нормальной поддержкой многопроцессной записи.
