# Архитектура

## Пайплайн

```
Long Poll (vkbottle) → фильтр себя → личка? (от ADMIN_ID — команда; от кого угодно
    ещё — игнор) → обрабатывается и выходит, в пайплайн не идёт никогда
  → гейт ALLOWED_PEER_IDS → фильтр дублей → команды в чате? (!вкл/!выкл — ADMIN_ID;
    !лимит/!лимиты — все) → обрабатываются и выходят, дальше не идут
  → склейка контекста (fwd_messages/reply_message — структурно, rule-based+LLM;
    предыдущее сообщение автора из in-memory кэша — только LLM) → pre-filter (тема?)
  → классификация+извлечение+резолв станции (LLM, если LLM_ENABLED и доступен; иначе/при сбое — rule-based)
      → отчёт: запись в БД (fuel_report/station_break/fuel_limit — все append-only, пишутся только если есть сигнал)
      → вопрос: факты по станции (марки + перерыв + лимит) → рендер шаблона
          → если станция не резолвилась, но вопрос похож на "сколько лимит на <бренд>" —
            статичный лимит бренда из gazetteer.yaml, в обход резолва станции
          → (если триггер сработал) отправка ответа
```

Генерация текста ответа — всегда через `templates.py`, независимо от того, кто делал разбор (LLM или regex). Это единственная защита от галлюцинаций: бот физически не может «нафантазировать» несуществующую АЗС или статус — шаблон использует только то, что реально есть в базе или в `gazetteer.yaml`.

## Компоненты

- `bot.py` — точка входа: инициализация `vkbottle.Bot` (**обязательно** `bot.labeler.message_view.replace_mention = True`, иначе `message.is_mentioned` всегда `False`, без ошибки — см. «Триггеры ответов»), запуск Long Poll.
- `config.py` — настройки из env: `VK_TOKEN`, `GROUP_ID`, `ALLOWED_PEER_IDS` (обязательная — allowlist обслуживаемых бесед, см. «Границы беседы»), `ADMIN_ID`, пороги свежести, `AUTO_REPLY_ON_QUESTION`, debounce, LLM-флаги.
- `vk_handlers.py` — обработчик `message_new`: гейт по беседе (`_is_allowed_peer`, первым делом — до дедупа и команд), отсечение собственных сообщений бота, идемпотентность, разбор команд `!вкл`/`!выкл`/`!лимит`/`!лимиты` (до пайплайна, см. «Команды в чате»), склейка контекста (`_quoted_context_text`, `_last_author_message` — только для LLM-ветки), диспетчеризация в пайплайн, отправка ответа (тег адресата, debounce).
- `pipeline/prefilter.py` — быстрый keyword-фильтр по теме (марки/бренды/типовые слова + голое «?»).
- `pipeline/extract.py` — regex-извлечение: марка+статус, очередь, технический перерыв, лимит отпуска; классификация отчёт/вопрос/нерелевантно. Rule-based путь и фолбэк для LLM-пути.
- `pipeline/resolve_station.py` — сопоставление текста с АЗС из `gazetteer.yaml` (бренд+локация), брендовые статичные лимиты (`get_brand_fuel_limit`, `get_displayed_brand_fuel_limits`). Rule-based путь и фолбэк для LLM-пути.
- `pipeline/facts.py` — дата-классы `QueueInfo`/`StationFact`/`StationBreak`/`StationLimit`, общий `MOSCOW_TZ`.
- `pipeline/pipeline.py` — `_analyze()`: LLM первым (если включён), при `None` — rule-based без изменений; `process_message()` — оркестрация записи в БД и ответа на вопрос (включая брендовый фоллбэк по лимиту).
- `pipeline/qa.py` — `answer_question()` (факты+перерыв+лимит по резолвленной станции), `answer_brand_limit_question()` (лимит по бренду без резолва станции).
- `llm/client.py` — диспетчер по `config.LLM_PROVIDER`, реэкспортирует `LLMAnalysis`/`_parse_arguments`.
- `llm/schema.py` — провайдер-агностичное ядро: схема полей, валидация ответа модели (включая проверку `station_id` через `is_known_station`).
- `llm/groq_client.py` / `llm/gemini_client.py` / `llm/mistral_client.py` — по одному вызову `raw_analyze(text) -> dict | None` на провайдера; `gemini_client.py` дополнительно конвертирует схему в нативный диалект Gemini.
- `llm/prompts.py` — системный промпт + `_stations_brief()`, который читает `gazetteer.yaml` заново при каждой сборке промпта (не кэширует на импорте, в отличие от `resolve_station.py`).
- `templates.py` — `render_station_answer` (компактный формат: марки с одинаковым статусом на одной строке, один timestamp в заголовке — см. «Формат ответа»), `render_brand_limits_list` (для `!лимит`).
- `db/schema.py`, `db/repo.py` — SQLite: `fuel_report`, `station_break`, `fuel_limit`, `auto_reply_setting`, `unresolved_mention`, `processed_message`. Идентичность станций в БД не хранится — единственный источник правды это `gazetteer.yaml`, в БД станция — просто `station_id`.
- `gazetteer.yaml` — вручную поддерживаемый список известных АЗС (id/название/бренд/адрес/алиасы) + `brand_fuel_limits`/`brand_fuel_limits_display`.
- `scripts/review_unresolved.py` — CLI: нераспознанные упоминания станций по частоте.
- `scripts/compare_llm_vs_rules.py` — сравнение LLM vs rule-based на фикстурах.
- `tests/` — pytest на чистых функциях пайплайна, фикстуры из реальных обезличенных сообщений.

## Модель данных

Всё в БД — **append-only логи**, ничего не перезаписывается (кроме `processed_message`, чисто дедуп). «Текущее состояние» всегда вычисляется на лету при запросе, не фоновой задачей:

- **`fuel_report`** — факт «марка X доступна/недоступна» на станции. Несколько отчётов подряд — подтверждение, не дубликат; если два недавних противоречат друг другу, это явно отражается в ответе.
- **`station_break`** — технический перерыв (слив/отстой/тех. перерыв) целиком по станции, не по марке. `qa.py::_latest_break` — **без окна активности**: последняя запись показывается всегда, с возрастом, без автодеактивации по таймауту.
- **`fuel_limit`** — факт «на станции лимит N л / без ограничений», **из чата**, привязан к конкретной станции. Та же логика «без окна активности», что у `station_break`.
- **`auto_reply_setting`** — состояние переключателя `!вкл`/`!выкл` (см. «Команды в чате»). Та же append-only форма.
- **`moderation_setting`** — состояние переключателя `!модерация` (см. «Модерация ответов»). Та же форма; сами черновики в БД не хранятся.

Ответ по станции показывает факты по маркам, перерыв и лимит **вместе**, один вид факта не подменяет другой.

Идентификация станции — по курируемому `gazetteer.yaml`, не по свободному тексту: `brand_aliases`/`location_aliases` матчатся независимо (`resolve_station.py`) — бренд с одной точкой резолвится по одному алиасу, бренд с несколькими точками — только если в тексте есть ещё и алиас локации; голое упоминание многоточечного бренда без локации уходит в `unresolved_mention`, если только это не единственный упомянутый бренд у которого задан `default_for_brand`. Отдельный запасной путь — резолв по одной лишь локации, если её алиас уникален по всему газетиру.

**`gazetteer.yaml::brand_fuel_limits`** — статичный лимит "в одни руки" **по бренду**, известный заранее (НЕ факт из чата, не то же самое, что `fuel_limit`). Нужен отдельно, потому что у многоточечных брендов голый вопрос без адреса ("сколько на РН?") не резолвит конкретную станцию, а лимит на неё всё равно нужно как-то показать — `answer_brand_limit_question()` отвечает лимитом бренда напрямую в обход резолва станции. Каждая запись — `{status: limited, liters: N}` или `{status: unlimited}`. `brand_fuel_limits_display` — курируемое подмножество брендов для команды `!лимит` (не обязательно совпадает со всем `brand_fuel_limits`).

**Известное, не исправленное ограничение**: и LLM, и rule-based поддерживают только один `station_id` на сообщение — сообщение про две станции сразу теряет факты по одной или уходит в `irrelevant`. Чинить — менять форму `ExtractResult`/tool schema на список станций, не однострочная правка.

## Границы беседы

Бот обслуживает **ровно те беседы, что перечислены в `ALLOWED_PEER_IDS`** (сейчас их две — прямое решение владельца). Сообщение из любой другой беседы отбрасывается первым же действием обработчика: не читается, не пишется в базу, не получает ответа, не участвует даже в дедупе. Первое сообщение из незнакомой беседы попадает в лог один раз — так видно, что сообщество куда-то добавили, но чужой чат не может залить лог.

Внутри allowlist **база фактов общая**: отчёт из одной беседы отвечает на вопрос в другой. Это осознанный выбор (обе беседы про одни и те же АЗС, общая история вдвое плотнее), а не побочный эффект — раньше `peer_id` знала только запись, а чтение не знало вовсе. Наружу при этом уходит только марка, статус и время: ни текста сообщения, ни автора в ответе нет. Разговорный контекст (`_last_author_message`) по-прежнему разделён по беседам — связность треда и общая база знаний это разные вещи.

Переменная обязательная, дефолта нет: пустое значение пришлось бы трактовать как «любая беседа», поэтому бот просто не стартует. См. ARCH_DECISIONS.md, Р4.

**Личка гейтом не проходит и в него не входит** — её разбирает отдельная ветка выше по обработчику (см. «Команды в личке»). Границу это не расширяет: из лички не читается и не пишется ни одного факта, туда уходят только ответы на команды владельца.

## Конкурентность

**Блокирует только вызов провайдера, и он уходит в отдельный поток** (`asyncio.to_thread` в `pipeline.py::_analyze`). Это единственное место, которое стоит секунд: 1.8 с в норме, ~10 с при сбое. Раньше оно держало весь цикл событий — сообщения не обрабатывались параллельно, а стояли в очереди, и во время всплеска бот не вычитывал новые события вовсе.

**БД остаётся в цикле событий.** Соединение SQLite привязано к потоку, в котором создано, поэтому вынос обработки в рабочий поток потребовал бы второго соединения и явных блокировок. Работа с базой занимает миллисекунды — выносить нечего.

**Что это меняет на практике** (живой замер, пять сообщений, Mistral): раньше все пять ответов уходили в самом конце, через ~5 с; теперь каждый готов через ~2.8 с. Задержка стала не столько меньше, сколько **равномерной** — провайдер обслуживает пять одновременных запросов медленнее, чем по одному, так что первый спросивший ждёт чуть дольше, а последний — заметно меньше.

**Атомарность там, где она нужна, сохранена.** Дедуп (`already_processed`) и проверка дебаунса идут без единого `await` внутри, а запись фактов — одной транзакцией без `await`. Появившийся `await` стоит только там, где идёт сетевой вызов.

**Время факта — из `message.date`, а не из момента записи.** При очереди разница уже не косметическая: именно это время решает, какой отчёт свежее. Неправдоподобная дата (нет, эпоха-ноль, будущее) заменяется временем обработки, naive-значение приводится к UTC.

## Отказы: что происходит и кто об этом узнаёт

**Одно сообщение — одна транзакция.** Факты (`fuel_report`/`station_break`/`fuel_limit`/`unresolved_mention`) и отметка «обработано» кладутся вместе, блоком `with conn:` в `pipeline.py::process_message`. Либо легло всё, либо ничего: сбой на середине не оставляет половину факта и не помечает сообщение обработанным. Функции `db/repo.py` поэтому сами не коммитят — транзакцией владеет вызывающий.

**Отметка «обработано» — после обработки, а не до.** Раньше сообщение помечалось первым делом, и любое исключение означало, что оно не обработано и никогда не будет: повторную доставку отбрасывал дедуп. Теперь повторный разбор того же сообщения безопасен — он просто перезапишет то же самое в ту же транзакцию.

**Семантика доставки — at-most-once, и это решение, а не побочный эффект.** VK не переспрашивает: `ts` продвигается до обработки, сообщения за время простоя пропускаются. Своей очереди повторов нет сознательно. Что сделано вместо неё: перехват вокруг всей обработки, один ретрай на отправку, и отказ декоративного `users.get` больше не уничтожает уже вычисленный ответ (раньше уничтожал — и снаружи это выглядело как обычное молчание).

**О сбое узнаёт владелец, в личку.** Необработанное исключение — сообщение на `ADMIN_ID`, не чаще раза в 10 минут. В алерт идут только беседа, номер сообщения и тип ошибки; текста участника там нет. Требует одноразового действия со стороны владельца: VK не даёт сообществу писать первым, пока пользователь не разрешил сообщения от него (иначе `VKAPIError_901`). Сбой доставки самого алерта ничего не ломает — остаётся строкой в логе.

**Чего это не закрывает:** смерть поллинга (контейнер остаётся `Up`, бот глухим) исключения не порождает, алерт на неё не сработает. Healthcheck сознательно не делался — см. ARCH_DECISIONS.md, Р8.

## Данные участников: что хранится и сколько

**Сам факт живёт вечно, всё остальное истекает.** Станция, марка, статус, время — навсегда; сырой текст сообщения (`raw_text`) обнуляется через `RAW_TEXT_TTL_DAYS` (30 суток), записи дедупа удаляются через `PROCESSED_MESSAGE_TTL_DAYS` (7 суток) — они нужны только для недавних сообщений.

**Это записанное исключение из append-only, а не тихое нарушение.** Принцип «не переписывать, а копить» защищает *факты*; срок жизни сырого текста — другое.

**Вместо VK-идентификатора хранится отпечаток.** `author_hash` — HMAC (blake2b) от id на локальном ключе (`AUTHOR_HASH_SECRET`, по умолчанию — токен сообщества). «Тот же автор» остаётся различим, конкретный человек — нет. В `author_id` новых строк пишется `0`; исторические значения обнуляются той же ретенцией. До этого в четырёх таблицах бессрочно лежали числовые id 87 реальных людей — **без единого читающего запроса**.

**Логи.** Строка на сообщение не содержит ни текста, ни идентификатора: беседа, отпечаток автора (8 символов), исход, длина текста, был ли контекст. Клиенты провайдеров при сбое пишут длину, а не текст. Приёмник loguru у vkbottle поднят с DEBUG до WARNING — иначе в поток попадало каждое сырое VK-событие целиком, вместе с `from_id` и текстом.

**Запуск уборки — без планировщика**: раз в час на живом трафике плюс один прогон на старте (`vk_handlers.run_retention_if_due`). Своего шедулера в проекте нет, а заводить его ради одной уборки — лишняя подсистема; нет трафика — нет и новых данных, которым нужно истекать.

**Осведомлённость участников** — вопрос закрыт владельцем 2026-08-16: в чате знают, что бот отслеживает сообщения. Технические меры выше от этого не отменяются, но отдельного объявления не требуется.

## Триггеры ответов

Ответ на вопрос отправляется, если бота явно упомянули **или** включён автоответ (флаг `AUTO_REPLY_ON_QUESTION` из `.env`, переопределяемый в БД командой `!вкл`/`!выкл` — см. ниже), плюс дебаунс как страховка от флуда.

**Дебаунс — на пару «беседа + автор»** (`MIN_REPLY_GAP_SECONDS`), а не на беседу целиком. Общее окно на весь чат означало, что при всплеске бот отвечает одному из пяти спросивших — ровно тогда, когда чат активен и бот полезнее всего. Поверх авторского окна стоит потолок на беседу (10 ответов в минуту) — страховка от патологического всплеска, а не от обычной активности; срабатывание пишется в лог, чтобы не быть ещё одним видом молчания.

**Важный нюанс vkbottle**: `message.is_mentioned` без `bot.labeler.message_view.replace_mention = True` в `bot.py` всегда `False`, без ошибки. Найдено только на живом тесте.

**Молчание вместо шаблонного «не знаю»**: если станция не распознана, или распознана, но по ней вообще нет фактов (ни марок, ни перерыва, ни лимита), `answer_question` возвращает `None`, ответ не отправляется — никакого «не понял»/«нет данных» в чат.

## Формат ответа

С Этапа 42 ответ отвечает на заданный вопрос, а не выкладывает всё известное о станции. Причина простая: ответ на «есть 95?» занимал четыре строки, из которых три были про то, чего не спрашивали.

```
инфа на 20-33.
92, 95 - Есть
```

- **Заголовок не повторяет станцию.** Бот отвечает реплаем на вопрос, где она уже названа. Время — в формате `ЧЧ-ММ`, берётся у самого свежего из показанных фактов.
- **Перерыв, лимит и очередь — только если о них спросили.** Тему вопроса определяют регулярки в `pipeline/qa.py` (`_BREAK_QUESTION_RE`, `_LIMIT_QUESTION_RE`, `_QUEUE_QUESTION_RE`) — не поле в схеме: так это одинаково работает на LLM-пути и на rule-based, без правок схемы, промпта и трёх клиентов, а приём в этом файле уже был (`_LIMIT_QUESTION_RE` для брендового лимита). Очередь при этом ещё и не дробит группы марок: раньше «92, 95 - Есть» распадалось надвое просто потому, что у марок разная очередь.
- **Только 92 и 95** (`ANSWERED_GRADES`). ДТ отслеживается, но в ответ не идёт; 98 и 100 не отслеживаются вовсе — см. `pipeline/facts.py` и «Известные пробелы».

Это разворот прежнего прямого решения («перерыв и марки показываем вместе, одно не подменяет другое», Этап 11). Оно отменено таким же прямым решением владельца: полнота проиграла ответу по существу.

### Команды в чате

Разбираются в `vk_handlers.py` до основного пайплайна (не идут через `is_on_topic`/классификацию/LLM) — голый текст сообщения целиком, без хвостов, регистр и пробелы по краям неважны.

- **`!вкл` / `!выкл`** — переключают `AUTO_REPLY_ON_QUESTION`. Доступны только `ADMIN_ID` (проверка по `from_id`). Состояние — в БД (`auto_reply_setting`), переживает рестарт/редеплой; `.env`-значение остаётся дефолтом, пока командой ни разу не пользовались.
- **`!лимит` / `!лимиты`** — статичный список лимитов по `brand_fuel_limits_display`. Доступна всем, без проверки `ADMIN_ID`, но с тем же debounce, что у обычных ответов (открыта всем — риск флуда реальнее, чем у admin-only команд).

### Команды в личке (канал управления)

Те же `!вкл`/`!выкл` доступны владельцу в личных сообщениях сообществу — чтобы не засорять живую беседу служебной перепиской (прямое пожелание владельца). Плюс `!помощь` — справка со всеми командами **и текущим состоянием** (автоответ, модерация, число ждущих черновиков); состояние читается из БД, не из `.env`, потому что там только дефолт. На любой другой текст бот отвечает той же справкой, чтобы канал не молчал непонятно.

Ветка стоит **до** гейта `ALLOWED_PEER_IDS`, и решение Р4 этим не размывается: гейт охраняет беседы, из которых берутся и в которые уходят факты, а из лички не пишется и не читается ни одного факта. Личка — канал управления, а не третий источник данных; `process_message` отсюда не вызывается вообще.

- Отличить личку от беседы можно по `peer_id`: у беседы это `2000000000 + номер`, у лички — VK-id отправителя. **Проверено живьём** на Long Poll (Этап 40), а не выведено из документации.
- Чужая личка игнорируется целиком и не получает ответа даже о том, что она чужая. В лог попадает один раз на человека и **отпечатком, а не `peer_id`**: в личке `peer_id` и есть идентификатор человека, а идентификаторам в логе не место (решение Р7).
- Разбор — `_parse_private_command`, отдельный от чатовых `_parse_admin_command`/`_is_limit_list_command`, и намеренно свободнее: допускает аргумент после имени команды. В беседе строгость нужна, чтобы обычная реплика по теме не сработала как команда; в личке единственный отправитель — владелец.
- Ответ уходит через `messages.send`, а не `message.reply`: этот путь уже проверен живьём на алертах владельцу (Р8) и не зависит от того, как VK трактует «ответ на сообщение» в личной переписке.
- Дебаунса и потолка ответов тут нет — они про беседу и живых людей; команды подряд отрабатывают все. Дедуп по `conversation_message_id` при этом общий с беседами.

### Модерация ответов (`!модерация`, с Этапа 41)

Ответ не уходит в беседу сразу, а приходит владельцу в личку карточкой с номером: вопрос участника, беседа и готовый текст. `+7` отправляет черновик №7 в ту же беседу, `-7` отклоняет, голые `+`/`-` — про последний. Режим переключается **голой командой `!модерация`** (прямое решение владельца — одна команда без аргументов); явные `!модерация вкл`/`выкл` тоже понимаются, чтобы набранное по привычке «вкл» при уже включённом режиме не выключило его. Состояние — в БД (`moderation_setting`, append-only, как `auto_reply_setting`), `MODERATION_ON_REPLY` из `.env` остаётся дефолтом.

- **Гейтится только исходящий текст.** Факты к моменту развилки уже записаны (`process_message` отработал выше), дебаунс и потолок ответов тоже. Режим придерживает публикацию, а не сбор: база копится ровно как обычно.
- **Отправляется ровно тот текст, который подтвердили** — ответ не пересчитывается в момент `+N`. Иначе владелец одобрял бы один текст, а в беседу уходил другой.
- **Черновики живут в памяти процесса**, не в БД: их срок — `MODERATION_TTL_MINUTES` (15 по умолчанию), переживать рестарт им незачем. Протухший черновик удаляется и **не отправляется**: автоотправка по таймауту убила бы смысл режима, а в тексте ответа стоит абсолютное время («на 18:40»), которое к тому моменту вводит в заблуждение.
- **Номера короткие и переиспользуются по кругу** (1..99): «+7» набрать с телефона проще, чем «+2137», а столкнуться двум живым черновикам с одним номером мешает срок жизни — одновременно их единицы.
- **Без `ADMIN_ID` режим не включается**: подтверждать некому, и бот молча съедал бы все ответы. В этом случае он отвечает напрямую и пишет об этом в лог (тихо деградировать в молчание — худший исход, находки G3-G5).
- Если карточка владельцу не доставлена, черновик не сохраняется: ждать подтверждения того, о чём никто не узнал, бессмысленно.
- Ответы на `!лимит` и подтверждения команд модерацию не проходят — она про ответы, собранные из фактов, а не про детерминированный вывод из `gazetteer.yaml`.

## LLM-анализ (опционально, `LLM_ENABLED`, `LLM_PROVIDER`)

Классификацию+извлечение+резолв станции можно передать LLM вместо `extract.py`/`resolve_station.py` — тремя провайдерами на выбор (`mistral` по умолчанию, либо `groq`/`gemini`), через forced tool calling с общей схемой (`llm/schema.py`). Ответ модели валидируется перед использованием (неизвестные значения молча отбрасываются, а не ломают разбор). Полная история выбора и сравнения провайдеров, живые проверки, конкретные цифры совпадения — в **PROGRESS.md, Этапы 4-6, 15-18**.

### Что происходит, когда LLM не отвечает

**Сначала — второй провайдер.** `LLM_FALLBACK_PROVIDER` (если задан и отличается от основного) пробуется прежде, чем разбор уйдёт на rule-based. Пусто — второй попытки нет.

**Дальше — асимметричный откат.** Rule-based продолжает разбирать **вопросы**, но теряет право писать **факты**. Причина в разной цене ошибки: rule-based ищет отрицание только перед маркой и в окне 20 символов, а запятая у него не разделяет клаузы, поэтому «95 закончился» читается как «есть» (находка B1). Такой факт оседает в append-only логе и повторяется в каждом будущем ответе про станцию — уже после того, как провайдер починился. Ошибка на вопросе живёт один ответ: текст всё равно собирается из БД шаблоном.

Гвард срабатывает **только при аварии**. Если LLM выключен намеренно (`LLM_ENABLED=false`), rule-based — штатный путь и право записи у него остаётся, иначе бот в этом режиме перестал бы копить данные вовсе.

**Колонка `source`** (`llm`/`rule_based`) в `fuel_report`/`station_break`/`fuel_limit` — чтобы задним числом было видно происхождение факта. У строк, записанных до её появления, там `NULL`.

**Провайдеры:**
- **Mistral** (`ministral-8b-2512`, по умолчанию с Этапа 18) — лимит по токенам/запросам **в минуту**, не по дням как у Groq; не требует SOCKS5-туннеля с library-vps (в отличие от Groq/Gemini — см. DEPLOY.md).
- **Groq** (`llama-3.3-70b-versatile`) — был дефолтом до Этапа 18; дневной лимит токенов (100k) реально исчерпывался на живом трафике в течение вечера.
- **Gemini** (`gemini-flash-lite-latest`) — лимит по RPM (~8-9/мин на бесплатном тарифе); через SOCKS5-туннель бота **не работает** (Google блокирует и сам внешний узел туннеля, не только российские IP) — на library-vps не используется.

Для всех трёх — датированная модель, не алиас `-latest`: `mistral-medium-latest`/`gemini-flash-latest` резолвятся в модели с заметно более тесными лимитами, чем нужные датированные версии.

**Открытый, не устранённый риск — модель может сфабриковать факт, не только ошибиться со станцией.** На реальном сообщении Groq в 4 из 6 повторов придумал недоступность марки, которой в тексте не было вообще. Это не «сбой» (ответ формально валиден) — существующая валидация ловит только заведомо невозможные `station_id`, не выдуманные `reports`. `queue_note` у LLM-пути был вторым слабым звеном — свободный текст модели уходил в чат почти без фильтра (находка F1, три инъекции из трёх); **закрыто**: очередь передаётся структурой (`QueueInfo`: статус + числа), текст собирает `templates.py::render_queue` из фиксированного словаря, легаси-колонка `queue_note` больше не читается. Теперь утверждение «текст ответа всегда рисует шаблон» верно без оговорок — но только про текст: сам факт модель по-прежнему может выдумать. Отдельно, не баг конкретно LLM, но усилившийся риск с Этапа 26/29: **включённый `!вкл` делает любую ошибку резолва станции видимой сразу всему чату**, а не только тем, кто явно тегнул бота — живой пример см. PROGRESS.md, Этап 28 (Mistral уверенно приписал вопрос не той станции Роснефти).

## Известные пробелы и открытые вопросы

- **Один `station_id` на сообщение** — см. «Модель данных» выше.
- **LLM может сфабриковать факт** — см. «LLM-анализ» выше.
- **Ретрай без бэкоффа на persistent-ошибках VK API** (найдено на Этапе 21 — бот ~3 часа долбил `groups.getLongPollServer` раз в секунду при бане сообщества, пока не заметили и не остановили вручную). Не починено — кандидаты: бэкофф в обработке ошибок long poll, уведомление при затяжной серии одинаковых ошибок через канал, не зависящий от VK (сам VK не может пожаловаться на свой же сбой).
- **Схема `FuelReport` не поддерживает факт про очередь без марки топлива** — LLM такие иногда находит, но писать некуда.
- **`_BREAK_KIND_WORDS`/промпт не покрывают все синонимы перерыва** — например «закрывается»/«были закрыты» не распознаются ни rule-based, ни (в контексте чата) LLM-путём.
- **Префильтр не знает про все локации газетира** — только явные бренды/марки плюс два точечных исключения («вилга», «стк» — единственные точки своего бренда, добавлены по факту живых сообщений). Остальные голые локации без бренда/цифры мимо анализа не проходят. Не расширяли на весь газетир осознанно — часть алиасов локаций (например «магнит», «правда») это обычные бытовые слова.
- **Короткие реплики в диалоге** («Есть.», «это на силикатном?») иногда классифицируются LLM как `question`, когда процитированный контекст содержит «?» — путает «вопрос где-то в контексте» с «текущее сообщение — вопрос». Эффект мягкий (гвард не даёт записать как отчёт).
- **Long Poll → Callback API**, если бот когда-нибудь расширится на несколько бесед/городов; тогда же пересмотреть SQLite в пользу БД с нормальной поддержкой многопроцессной записи.
- **OCR/vision-анализ фото** ценников и очередей — не делали, провайдеры (Groq/Llama) технически умеют мультимодальный ввод.
