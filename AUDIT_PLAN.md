## Карта проекта (исходные данные для плана)

**Один процесс**: `bot.py` → vkbottle Long Poll → `vk_handlers.on_message` (единственный
async-слой и единственная точка I/O с VK) → `pipeline.process_message` (полностью
синхронный, включая HTTP-вызовы к LLM) → SQLite (`db/repo.py`, один коннекшен на процесс,
открытый на импорте `vk_handlers.py:16`).

**Два независимых пути разбора** одного сообщения: LLM (`llm/*`, три провайдера) и
rule-based (`pipeline/extract.py` + `resolve_station.py`), с прозрачным откатом первого на
второй. Пути получают **разный вход** (LLM — `own_text` + размеченный контекст, rule-based —
плоскую склейку `text`), и часть логики пайплайна (гвард «репорт всплыл только из цитаты»,
`pipeline.py:97`) при любом пути считается только rule-based механизмом.

**Данные**: пять append-only таблиц + одна дедуп-таблица, без индексов (кроме autoindex по
PK), без CHECK/FK, без миграций, без ретенции. Идентичность станций живёт не в БД, а в
`gazetteer.yaml`, который правится вручную на проде и не валидируется ничем.

**Инфраструктура**: Docker Compose на тесном VPS (961Mi RAM, ~1.8G диска, два чужих стека
рядом), сайдкар SOCKS5-туннеля, CI нет, бэкапов нет (сознательно), локально Python 3.14, в
образе 3.12.

## Этап 3. Бизнес-логика и корректность разбора (ядро аудита)

**Что проверять**
- **Классификация**: `_QUESTION_MARKERS` (`extract.py:12`) содержит голый `\?` — любое
  сообщение с вопросительным знаком становится `question` целиком, включая отчёт,
  заканчивающийся вопросом.
- **Извлечение марок**: разбиение на клаузы по `[.\n!]+` (не по `,` и `?`); окно отрицания
  «20 символов до»; исключение «100 л» (`extract.py:121`); ordinal-суффиксы.
- **Резолв станции**: независимый матчинг бренда и локации; `default_for_brand`; фоллбэк

- **Гвард «репорт только из цитаты»** (`pipeline.py:97`): вызывает `extract(own_text)`, то
  есть при LLM-пути решение принимает rule-based механизм. Заявленное или случайное?
- **Брендовый фоллбэк по лимиту**: `answer_brand_limit_question(text)` (`pipeline.py:94`)
  получает склеенный с цитатой текст — может ли бренд из цитаты породить ответ?
- **Рендер перерыва**: `_render_break_line` (`templates.py:50`) при непустом `until`
  показывает «ожидается до HH:MM» без возраста, а `until` резолвится всегда на сегодняшний
  московский день (`extract.py:57`).
- **Свежесть и конфликты**: `_tier_for_age`, флаг `conflicting` (только 2 последних отчёта
  на марку), группировка марок в `_render_grouped_fact_lines`.
- **Молчание как продукт**: все пути, где `answer_question` возвращает `None`, и все пути,
  где бот отвечает при пустых данных.

**Файлы**: `pipeline/extract.py`, `pipeline/resolve_station.py`, `pipeline/qa.py`,
`pipeline/pipeline.py`, `templates.py`, `tests/fixtures.py`, `gazetteer.yaml`, `PROGRESS.md`.

## Этап 4. Работа с данными и БД

**Что проверять**
- **Индексы**: их нет. Запросы `qa.py` — `WHERE station_id = ? ORDER BY reported_at DESC` по
  растущим таблицам, причём `_latest_facts` вытягивает все строки станции и фильтрует до 2
  на марку в Python (`qa.py:34-38`).
- **Целостность**: нет CHECK на `status`/`fuel_grade`/`kind`, нет FK, `station_id` связан с
  газетиром только по соглашению. Что произойдёт с историческими строками при переименовании
  id станции.
- **Время**: ISO-строки с tz; `datetime.fromisoformat` без защиты от naive-значения.
- **Транзакции**: `commit()` на каждый insert; сообщение с несколькими фактами пишется
  несколькими транзакциями (`pipeline.py:114-146`) — частичная запись при сбое.
- **Ретенция**: `processed_message` растёт вечно; `raw_text` хранится бессрочно.
- **Миграции**: `CREATE TABLE IF NOT EXISTS` при каждом подключении; добавление колонки не
  поддержано никак.
- **Бэкапы**: отсутствуют сознательно — что именно теряется и восстановимо ли.

**Файлы**: `db/schema.py`, `db/repo.py`, `pipeline/qa.py`, `docker-compose.yml`, `DEPLOY.md`.

**Вопросы**: Реальный объём `bot.db` на проде и темп роста? Сколько живут данные? Что должно
происходить при переименовании станции в газетире?

**Что искать**: деградацию запросов; невалидные значения, попавшие историческим путём;
данные-сироты; риск повреждения WAL при пересоздании контейнера.

**Почему важно**: append-only означает, что любой мусор остаётся навсегда и продолжает
влиять на ответы (окна активности у перерыва и лимита нет намеренно).

## Этап 5. Внешние интеграции: VK API и LLM-провайдеры

**Что проверять**

*VK:*
- `bot.labeler.message_view.replace_mention = True` (`bot.py:18`) — единственная защита от
  тихого отказа триггера; что не даст его потерять при рефакторинге.
- `users.get` на каждый ответ (`vk_handlers.py:81`) без try/except: его сбой уничтожает уже
  сформированный ответ.
- Обработка ошибок Long Poll: ретрай без бэкоффа (известный пробел, Этап 21).
- Что делает vkbottle с исключением из хендлера.

*LLM:*
- Три разных способа задать таймаут: `timeout=` (Groq), `timeout_ms=` + httpx-таймаут при
  прокси (Mistral, `mistral_client.py:31-33`), `HttpOptions.timeout` в мс (Gemini).
- Форма ответа Mistral — `Union[dict, str]`, обрабатываются оба варианта, живьём подтверждён
  один (комментарий `mistral_client.py:71-73`).
- Ретраев и бэкоффа нет; любой сбой → тихий откат на rule-based без метрики.
- Размер промпта (весь газетир в каждом запросе) и стоимость вызова.
- Валидация ответа (`llm/schema.py`) закрывает всё, кроме `queue_note` — см. этап 6.

**Файлы**: `vk_handlers.py`, `bot.py`, `llm/*.py`, `config.py`, `DEPLOY.md`.

**Вопросы**: Как узнать, что бот сутки работает на rule-based из-за лимита? Какой процент
сообщений уходит в LLM? Есть ли алерт хоть на что-нибудь?

**Что искать**: тихую деградацию качества; сбой одного вызова, уничтожающий ответ; таймаут,
который не применяется; ретрай-петли.

**Почему важно**: обе интеграции уже вели себя неожиданно на живом трафике (дневной лимит
Groq, бан сообщества).

**Зависит от**: этапов 1, 3. **Влияет на**: этапы 6, 7, 8, 9.

## Этап 6. Безопасность, авторизация и приватность

**Что проверять**
- **Авторизация**: единственная проверка прав — `message.from_id == ADMIN_ID`
  (`vk_handlers.py:99`). При незаданном `ADMIN_ID` команды молча мертвы.
- **Область действия**: `peer_id` не проверяется нигде. Бот обслуживает любую беседу, куда
  его добавили, пишет факты в общую БД и отдаёт `!лимит` кому угодно.
- **Prompt injection**: текст участника попадает в промпт, `queue_note` возвращается моделью
  как свободная строка и печатается в чат почти без фильтра (`schema.py:166`,
  `templates.py:104`).
- **Флуд**: дебаунс 5 секунд на беседу; `!лимит` открыт всем и делит этот дебаунс с
  содержательными ответами.
- **Секреты**: `.env` не в git, но попадает в контейнер через `env_file`; ключ туннеля —
  bind-mount; `StrictHostKeyChecking=yes` настроен корректно.
- **Приватность**: `log.info` пишет полный текст сообщения + `from_id`
  (`vk_handlers.py:129`); `raw_text` хранится бессрочно; фикстуры при этом сознательно
  обезличены.
- **Контейнер**: процесс работает от root (в `Dockerfile` нет `USER`).

**Файлы**: `vk_handlers.py`, `config.py`, `llm/schema.py`, `templates.py`, `Dockerfile`,
`docker-compose.yml`, `docker/ai-proxy/*`, `.gitignore`, `.dockerignore`.

**Вопросы**: Кто может добавить сообщество в другую беседу? Задан ли `ADMIN_ID` на проде со
значением? Согласны ли участники на бессрочное хранение сообщений? У кого доступ к VPS?

**Что искать**: возможность заставить бота сказать произвольный текст; команды не тем;
утечку токена в логи/образ; данные людей без срока хранения.

**Почему важно**: бот пишет от имени сообщества в живой чат, и часть текста ответа приходит

## Этап 7. Обработка ошибок и надёжность

**Что проверять**
- **Порядок дедупа**: `mark_processed` вызывается до обработки (`vk_handlers.py:94`) —
  семантика at-most-once, любое исключение дальше означает потерю сообщения навсегда.
- Единственные `try/except` — внутри LLM-клиентов и в `llm/client.py`. Ни `process_message`,
  ни отправка ответа, ни `users.get` не защищены.
- Отсутствие бэкоффа на persistent-ошибках VK.
- Сбои старта: `config.py` падает по KeyError без секретов, `resolve_station.py` и
  `llm/prompts.py` — на битом газетире. При `restart: unless-stopped` это рестарт-петля.
- Наблюдаемость: только логи в stdout + json-file (10m×3), алертов нет. vkbottle логирует
  через loguru, код — через logging: что реально попадает в вывод контейнера.
- Graceful shutdown: соединение SQLite не закрывается явно.

**Файлы**: `vk_handlers.py`, `bot.py`, `pipeline/pipeline.py`, `db/schema.py`,
`docker-compose.yml`, `DEPLOY.md`, `ARCHITECTURE.md`.

**Вопросы**: Как владелец узнаёт, что бот молчит? Сколько сообщений уже потеряно тихо?
Приемлема ли потеря сообщения при сбое?

**Что искать**: пути, где ошибка = молчание; рестарт-петли; логи, в которых сбоя не видно.

**Почему важно**: бот работает без присмотра, а его отказ выглядит для чата ровно так же,

# Critical paths

Части, где ошибка видна снаружи и необратима:

1. **`vk_handlers.on_message` целиком** (`vk_handlers.py:88-149`) — единственная точка, где
   бот читает и пишет в чат. Дедуп, авторизация команд, гейт по упоминанию, дебаунс,
   отправка. **Не покрыта тестами.**
2. **`_analyze` → `station_id`** (`pipeline/pipeline.py:21-54`) — развилка LLM/rules и
   источник самой дорогой ошибки: факт, приписанный не той АЗС. Формально валидна, ничем не
   ловится, с `!вкл` видна всему чату.
3. **Запись в БД** (`pipeline.py:114-146` + `db/repo.py`) — append-only: ложный факт остаётся
   навсегда.
4. **`answer_question` + `templates.py`** — заявленная единственная защита от галлюцинаций.
   Проверить, что ни один путь не даёт LLM-тексту попасть в ответ в обход шаблона.
5. **Старт процесса**: `config.py` → `resolve_station.py` → `llm/*_client.py`. Исключение
   здесь = бот не поднимается, а `restart: unless-stopped` даёт петлю.
6. **Дедуп `processed_message`** — защита от повторов после рестарта и одновременно причина
   потери сообщения при сбое.

# Areas of uncertainty

| Что неизвестно | Как проверить |
|---|---|
| Реальные значения `.env` на library-vps (`ADMIN_ID` со значением? `LLM_ENABLED`?) | SSH + чтение значений, не grep по наличию строки |
| Размеры `bot.db` и темп роста на проде | `docker exec` + запросы по количеству строк |
| Частота отката LLM→rule-based на живом трафике | Подсчёт `path=rule_based reason=llm_fallback` в логах |
| Параллельность обработки событий в vkbottle и судьба исключения из хендлера | Чтение кода vkbottle 4.10.0 + эксперимент |
| Блокирует ли синхронный LLM-вызов приём следующих сообщений | Замер на двух сообщениях подряд при замедленном провайдере |
| Реальная форма `arguments` у Mistral (dict или str) | Один живой вызов с логированием типа |
| Фактические лимиты ключа Mistral и текущее потребление | Панель провайдера + счётчик вызовов |
| Настройки сообщества VK: кто может добавить бота в беседу | Проверка настроек сообщества |
| Свободные память/диск на VPS и потребление контейнера | `df -h /`, `docker stats --no-stream`, `free -m` |
| Можно ли prompt-injection'ом заставить бота напечатать произвольный текст | Контролируемый тест `queue_note` в тестовой беседе |

# Expected risks (гипотезы, не находки)

Видно по структуре, подлежит проверке; ни один пункт не подтверждён как дефект.

**Высокий приоритет проверки**
1. Синхронный LLM-вызов внутри async-хендлера блокирует event loop до 10 секунд.
2. `mark_processed` до обработки даёт безвозвратную потерю сообщения при исключении, в том
   числе при сбое `users.get`.
3. `queue_note` — свободный текст от модели, проверяемый только на непустоту, печатается в
   чат: канал prompt-injection в исходящее сообщение.
4. Ретрай без бэкоффа на persistent-ошибках VK.
5. `answer_brand_limit_question` получает склеенный с цитатой текст — бренд из чужой цитаты
   может породить ответ.

**Средний приоритет**
6. «Ожидается до HH:MM» без возраста + резолв `until` всегда на сегодня — вчерашний перерыв
   выглядит как предстоящий.
7. Голый `\?` делает вопросом любой отчёт с вопросительным знаком.
8. Гвард «репорт только из цитаты» использует rule-based `extract` даже на LLM-пути.
9. Отсутствие индексов + бессрочный рост таблиц.
10. `LLM_ENABLED=true` с пустым ключом = тихий вечный rule-based без сигнала.
11. Ручная правка газетира на проде без валидации → падение на импорте и рестарт-петля.
12. `!лимит` открыт всем и делит дебаунс с содержательными ответами.

**Ниже, но учесть**
13. Бессрочное хранение `raw_text` + полные тексты и `from_id` в логах.
14. Контейнер от root; нет лимитов памяти при 961Mi на три стека.
15. `_last_author_message` растёт без вытеснения.
16. Транзитивные зависимости не зафиксированы.
17. Дрейф документации (например, утверждение о некэшируемости промпта).
18. Прод на Python 3.12, тесты на 3.14 при отсутствии CI.
