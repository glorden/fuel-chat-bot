# CLAUDE.md

Инструкции для Claude Code при работе в этом репозитории.

## Проект

VK-бот для тематической беседы про заправку топливом. Дизайн — в [ARCHITECTURE.md](ARCHITECTURE.md), статус — в [PROGRESS.md](PROGRESS.md), деплой — в [DEPLOY.md](DEPLOY.md).

## Рабочий процесс (важно, соблюдать строго)

После завершения каждого этапа из `PROGRESS.md`:
1. Прогнать проверки этого этапа.
2. `git commit` — отдельный коммит по смыслу этапа (не смешивать этапы).
3. `git push`.
4. Обновить `PROGRESS.md` (отметить этап, дата, короткий итог).
5. **Остановиться.** Дать короткий итог (что сделано, что проверено) и предложить следующий шаг. Дождаться подтверждения пользователя, прежде чем начинать следующий этап.

Не забегать вперёд на несколько этапов за один проход, даже если следующий шаг кажется очевидным.

## Ключевые решения

- **LLM — опционален, флагом `LLM_ENABLED` (по умолчанию `false`); провайдер выбирается `LLM_PROVIDER` (`mistral` по умолчанию — сменили с `groq` на Этапе 18, у Groq дневной лимит токенов реально исчерпался на живом трафике; либо `groq`/`gemini`).** Классификация+извлечение+резолв станции могут идти через `llm/client.py` (тонкий диспетчер → `llm/groq_client.py`/`llm/gemini_client.py`/`llm/mistral_client.py`, tool/function calling) вместо `extract.py`/`resolve_station.py` — при любом сбое/лимите/невалидном ответе прозрачный откат на них же, они не удаляются и не переписываются. Провайдер-агностичное ядро (схема полей, парсинг ответа) — в `llm/schema.py`, общее для всех провайдеров; Mistral, в отличие от Gemini, использует эту схему без конвертации. **Генерация текста ответа всегда через `templates.py`, никогда через LLM** — единственная защита от галлюцинаций (бот не может написать статус, которого нет в БД; но LLM всё же может нафантазировать сам факт в `reports` — живая находка с Groq, подтверждённый и не устранённый риск, см. ARCHITECTURE.md «Известные пробелы»). Детали выбора провайдеров, живые сравнения и конкретные цифры — PROGRESS.md, Этапы 4-6, 15-18.
- **`FuelReport` — append-only лог.** Не переписывать статус в БД, а копить отчёты. «Текущий статус» и «свежесть» — вычисляются на лету при запросе, не фоновой задачей.
- **`StationBreak` (`station_break`, с Этапа 11) — тоже append-only лог**, отдельный от `FuelReport`: технические перерывы/слив бензовоза — факт про станцию целиком, не про марку. `qa.py::_latest_break` — по прямому решению пользователя, **без окна активности**: всегда показывается последняя запись по станции, с возрастом, без автоматического «протух через N минут» — перерыв, о завершении которого никто не написал, упоминается сколь угодно долго с растущим «сообщили N назад». Не возвращать к идее автоматической деактивации без явного запроса. Ответ про станцию показывает перерыв и факты по маркам **вместе**, одно не подменяет другое (тоже прямое решение пользователя).
- **Станции резолвятся по `gazetteer.yaml`**, не по свободному тексту напрямую. Нераспознанные упоминания — в `UnresolvedMention`; новые станции в gazetteer добавляются вручную, не автоматически.
- **`gazetteer.yaml::brand_fuel_limits` (с Этапа 22) — статичный лимит отпуска "в одни руки" по бренду**, НЕ то же самое, что `fuel_limit` в БД (факты из чата про конкретную станцию, append-only, без окна активности — см. выше принцип `StationBreak`). У Роснефти/Татнефти/Лукойла по нескольку точек, и голый бренд без адреса в вопросе ("сколько дают на РН?") не резолвится ни в одну станцию через `resolve_station()` — `pipeline/qa.py::answer_brand_limit_question()` отвечает статичным лимитом напрямую, в обход резолва станции, только когда обычный `answer_question` не дал ответа именно из-за `station_id is None`, и только на вопросах, явно похожих на «сколько лимит/можно/дают/отпускают». **Не** фоллбэк, когда станция резолвится, но по ней просто нет отчётов, — молчание остаётся молчанием (Этап 5). Каждая запись — `{status: limited, liters: N}` или `{status: unlimited}` (форма `LimitInfo`/`StationLimit`) — `get_brand_fuel_limit()` возвращает `LimitInfo`, не голое число.
- **`!лимит`/`!лимиты` (с Этапа 29) — команда в чате, список статичных лимитов, доступна всем** (в отличие от `!вкл`/`!выкл` — без проверки `ADMIN_ID`). Показывает не весь `brand_fuel_limits`, а курируемое подмножество — `gazetteer.yaml::brand_fuel_limits_display` (по решению пользователя: Роснефть/Татнефть/Лукойл/Газпром, СТК сознательно не входит). `pipeline/resolve_station.py::get_displayed_brand_fuel_limits()` + `templates.py::render_brand_limits_list()`.
- **Оба режима триггера (упоминание бота / автоответ на любой вопрос) реализованы сразу, переключаются `AUTO_REPLY_ON_QUESTION`** (по умолчанию `false`). С Этапа 26 — ещё и командами `!вкл`/`!выкл` в чате, без деплоя: только `ADMIN_ID` (проверка по `from_id`), разбираются в `vk_handlers.py::_parse_admin_command` до пайплайна. Состояние — в БД (`auto_reply_setting`, append-only, как `station_break`/`fuel_limit` — последняя запись побеждает), не в `.env`: бот не переписывает свой конфиг-файл, а `.env`-значение остаётся дефолтом, пока командой не воспользовались. Переживает рестарт/редеплой — раньше (Этапы 19-20) переключить можно было только через SSH+`.env`+`--force-recreate`.
- **Ровно две беседы, allowlist `ALLOWED_PEER_IDS` (с Этапа 33) — прямое решение пользователя, «не меньше и не больше».** Гейт стоит первым действием в `vk_handlers.py::on_message`, до дедупа и разбора команд: из чужой беседы не читаем, не пишем, не отвечаем. Переменная обязательная, без неё бот не стартует (пустое значение = «любая беседа» — ровно та дыра, которую закрываем). База фактов внутри allowlist **общая**: отчёт из одной беседы отвечает на вопрос в другой — тоже прямое решение. Не добавлять третью беседу и не вводить скоуп фактов по `peer_id` без явного запроса.
- **Long Poll API**, не Callback — не требует публичного сервера, достаточно для одной беседы.
- **`bot.labeler.message_view.replace_mention = True` обязателен в `bot.py`.** Без него vkbottle тихо (без ошибки) никогда не распознаёт упоминания бота — `message.is_mentioned` всегда `False`. Нашли только на живом тесте, не из документации.
- **Пороги свежести калиброваны под этот чат, не универсальные дефолты**: `FRESH_MINUTES=240` (4 часа), `STALE_MINUTES=480` (8 часов) — по прямому запросу пользователя, информация о заправках тут живёт часами, не минутами. Не возвращать к «стандартным» 20/120 без явного запроса.
- **Контекст между сообщениями (с Этапа 9-10) — только для чтения текущего сообщения, не для записи фактов.** `vk_handlers.py` подклеивает текст `fwd_messages`/`reply_message` (структурная связь VK, rule-based+LLM) и держит короткоживущий in-memory кэш последнего сообщения автора (только LLM-путь, TTL 120 сек, не персистентный — не переживает рестарт бота). `process_message()` пишет факт в БД, только если *собственный* текст автора сам по себе несёт сигнал (`own_text` kwarg + гвард в `pipeline.py`) — иначе случайный «спасибо»-реплай на чужой отчёт искусственно освежил бы старый факт под новым timestamp.
- **Один `station_id` на сообщение — известное, не исправленное ограничение**, подтверждённое повторно на живых сообщениях (см. PROGRESS.md). Сообщение про две разные станции сразу теряет факты по одной из них или уходит в `irrelevant`. Чинить — значит менять форму `ExtractResult`/tool schema на список станций, это осознанно отложено, не однострочная правка.

## Команды

- Запуск бота: `python bot.py`
- Тесты: `pytest`
- Обзор нераспознанных упоминаний станций: `python -m scripts.review_unresolved`
- Сравнение LLM vs rule-based на известных сообщениях: `python -m scripts.compare_llm_vs_rules`

Скрипты в `scripts/` запускать через `-m` (`python -m scripts.имя`), не напрямую (`python scripts/имя.py`) — иначе Python не найдёт `pipeline`/`db`/`llm` в sys.path (он добавляет папку скрипта, а не корень проекта).
