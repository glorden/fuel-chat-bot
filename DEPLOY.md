# Деплой

Docker Compose на VPS, геолоцированном в России. Публичный HTTPS не нужен —
Long Poll исходящий, входящих портов боту не требуется вообще. Единственная
сложность — оба LLM-провайдера (Groq, Gemini) блокируют запросы из России на
уровне API-вендора, поэтому исходящие вызовы к ним заворачиваются в
SOCKS5-туннель (см. ниже).

## Переменные окружения

| Переменная | Обязательна | Описание |
|---|---|---|
| `VK_TOKEN` | да | Токен сообщества. Нужны права **«Управление сообществом» + «Сообщения сообщества»** — только «Сообщения» даёт ошибку 15/1133 на `groups.getLongPollServer` (см. PROGRESS.md, Этап 1). |
| `GROUP_ID` | да | Числовой id сообщества (без минуса). |
| `ADMIN_ID` | нет | Не используется активно сейчас, зарезервировано. |
| `AUTO_REPLY_ON_QUESTION` | нет (`false`) | Автоответ на распознанный вопрос по теме без явного упоминания бота. По умолчанию выключен — см. ARCHITECTURE.md, «Триггеры ответов». |
| `FRESH_MINUTES` | нет (`240`) | Порог «свежо» — откалиброван под этот чат (4 часа), не менять на «стандартные» значения без явного запроса. |
| `STALE_MINUTES` | нет (`480`) | Порог «устарело→старо» (8 часов). |
| `MIN_REPLY_GAP_SECONDS` | нет (`5`) | Дебаунс между ответами бота в чате. |
| `LLM_ENABLED` | нет (`false`) | Включает LLM-путь классификации поверх rule-based (см. ниже, «Процедура», шаг 6 — включать отдельным, проверяемым шагом, не сразу с первым деплоем). |
| `LLM_TIMEOUT_SECONDS` | нет (`10`) | Таймаут вызова LLM. |
| `LLM_PROVIDER` | нет (`groq`) | `groq`, `gemini` или `mistral`. На library-vps — `groq` изначально, но у него дневной (не по минутам) лимит токенов, реально исчерпывающийся на живом трафике (см. «Известное ограничение» и PROGRESS.md, Этап 16) — `mistral` не требует туннеля вообще (см. ниже) и лимитирован по минутам, а не по дням, поэтому меньше подвержен этому конкретному отказу. |
| `GROQ_API_KEY` | если `LLM_PROVIDER=groq` | Ключ Groq. |
| `LLM_MODEL` | нет (`llama-3.3-70b-versatile`) | Модель Groq. |
| `GEMINI_API_KEY` | если `LLM_PROVIDER=gemini` | Ключ Gemini. |
| `GEMINI_MODEL` | нет (`gemini-flash-lite-latest`) | Модель Gemini. |
| `MISTRAL_API_KEY` | если `LLM_PROVIDER=mistral` | Ключ Mistral. |
| `MISTRAL_MODEL` | нет (`ministral-8b-2512`) | Модель Mistral — датированная, не алиас `-latest` (см. ARCHITECTURE.md, та же ловушка лимитов, что и на Gemini). |
| `AI_PROXY_URL` | нет | `socks5h://ai-proxy:1080` — включает проксирование вызовов Groq/Gemini через сайдкар-туннель. Пусто — вызовы идут напрямую (и на library-vps не работают, см. ниже). |
| `AI_PROXY_SSH_HOST` | если `AI_PROXY_URL` задан | Адрес внешнего сервера, на который туннелирует сайдкар `ai-proxy`. |
| `AI_PROXY_SSH_USER` | нет (`tunneluser`) | Пользователь на внешнем сервере для туннеля. |
| `AI_PROXY_SSH_PORT` | нет (`22`) | SSH-порт внешнего сервера. |

## Ресурсы library-vps: на что рассчитывать

Бот деплоится на существующий VPS (`185.228.235.148`), который уже держит два
чужих проекта на Docker Compose: `travel-taxiptz` и `home-library-catalog`
(book library, каталог книг — тоже проект этого пользователя, но полностью
независимый). Ресурсы там реально тесные, не гипотетически:

- **Диск**: `8.7G` всего, обычно занято ~80%, свободно порядка **1.8G**.
  Docker build cache на хосте сам по себе может занимать сотни MB.
- **Память**: **~961Mi** всего, свободно/available от ~150 до ~460Mi в разные
  моменты. Своп 2GiB есть (обычно ~1.5GiB свободно) — реальный запас, но не
  повод не следить за потреблением.

Правила, чтобы не задеть чужие сервисы на этом же хосте:

- **Перед первой сборкой — `docker builder prune -f`**. Безопасен (чистит
  только build-кэш, не трогает образы/контейнеры других стеков), но при 1.8G
  свободных это не «на всякий случай», а обязательный шаг.
- **Никогда не `docker image prune -a`** на этом хосте бездумно — может
  снести образы, на которые ссылаются `travel-taxiptz`/`home-library-catalog`.
  Чистить точечно, по конкретному тегу/id, если вообще понадобится.
- **Ни `app`, ни `ai-proxy` этого проекта не публикуют `ports:`** — нулевой
  риск конфликта с портами 80/443 (Caddy у book library) или чем-либо ещё.
  Docker Compose сам изолирует проект по имени директории — отдельная
  default-сеть, коллизий с чужими сетями не будет.
- **Свой собственный SSH-ключ и свой `ai-proxy`-контейнер** — не переиспользуют
  и не трогают `home-library-catalog-ai-proxy-1` и его `secrets/` (см. ниже,
  почему это отдельная копия, а не общий сервис).
- После `docker compose up` — сверять `docker ps -a` (все контейнеры других
  стеков всё ещё `Up`), `df -h /`, `docker stats --no-stream` — до перехода к
  следующему шагу процедуры, не post-factum.

## AI-провайдер из заблокированной страны (SOCKS5-туннель)

Прод-VPS геолоцирован в России — Groq и Google (Gemini) режут запросы с
российских IP на уровне API-вендора, не по вине конфига. Проверено вживую с
самого library-vps: прямой запрос к `api.groq.com` и к
`generativelanguage.googleapis.com` — оба **`403`** за <200мс (это edge/geo-блок,
не настоящий ответ бэкенда — реальный ответ на невалидный/отсутствующий ключ
выглядел бы как `401`). VK API при этом отвечает `200` без всякого прокси —
это российский сервис, проксировать его не нужно, только вызовы LLM.

Решение — не переносить весь VPS, а завернуть исходящие вызовы `llm/groq_client.py`
/`llm/gemini_client.py` в SOCKS5-туннель через SSH на сервер вне блокировки.
Приём скопирован у соседнего проекта (`book library/DEPLOY.md`, «Шаг 9») —
там та же проблема была решена раньше для Claude/OpenAI-совместимого
провайдера. Здесь — **независимая копия**, не общая инфраструктура: свой
контейнер, свой SSH-ключ, свой `secrets/`. Общий только внешний сервер-цель
(личный сервер пользователя вне России) — если у book library когда-нибудь
изменится или отключится его туннель, это никак не заденет бота, и наоборот.

### Устройство

Сайдкар `ai-proxy` (`docker/ai-proxy/`) держит один процесс `ssh -N -D
0.0.0.0:1080` наружу, на `AI_PROXY_SSH_HOST`. Порт 1080 никуда не
публикуется (`ports:` нет в `docker-compose.yml`) — виден только сиблингу
`app` по compose-сети этого проекта, то есть без аутентификации на уровне
SOCKS (не нужна — тот же уровень доверия, что уже принят у book library для
его `db`: изоляция обеспечивается тем, что порт в принципе не выходит за
пределы приватной сети контейнеров).

В `llm/groq_client.py`/`llm/gemini_client.py` `AI_PROXY_URL` (если задан)
оборачивается в `httpx.Client(proxy=AI_PROXY_URL)` и передаётся в SDK через
`http_client=`/`http_options.client_args` при создании клиента (один раз, на
уровне модуля, не на каждый вызов). При пустом `AI_PROXY_URL` поведение не
меняется — прямые вызовы, как раньше (актуально для локальной разработки:
там прокси не нужен и не настроен).

### Внешний сервер: минимальные требования, не полная настройка с нуля

Внешний сервер под туннель — личный сервер пользователя вне России, уже
используемый под другую задачу (Xray/x-ui), не часть инфраструктуры этого
или book-library проекта. Поэтому здесь не нужен полноценный чек-лист «VPS с
нуля» — только:

- Пользователь без шелла для туннеля (`tunneluser`, вероятно уже существует —
  заведён под туннель book library; можно и нужно добавить **второй**,
  независимый ключ в тот же аккаунт, а не заводить нового пользователя —
  изоляция и так полная на уровне ключа/контейнера).
- Пара ключей генерируется **на library-vps** (`ssh-keygen` прямо на VPS, не
  на машине разработчика) и живёт в `secrets/ai_proxy_id_ed25519` (гитигнор,
  никогда не коммитится). Публичная часть — в `authorized_keys` у
  `tunneluser` на внешнем сервере, с опцией `restrict,port-forwarding`
  (отключает PTY/exec/agent-forwarding, оставляет только port-forwarding —
  ключ физически не может ничего, кроме `-D`).
- `sshd_config` внешнего сервера не трогается — это чужая, уже
  сконфигурированная под другие задачи машина.
- `known_hosts` фиксируется один раз через `ssh-keyscan` (с library-vps, при
  первой настройке) и живёт в `secrets/ai_proxy_known_hosts` — TOFU разово,
  не генерируется заново при каждом старте контейнера.

### Mistral не требует туннеля

В отличие от Groq/Gemini, прямой вызов `api.mistral.ai` с library-vps (без
`AI_PROXY_URL`) дал `401`, не `403` — Mistral (французская компания, не под
американскими экспортными ограничениями) Россию, похоже, не блокирует.
`llm/mistral_client.py` всё равно поддерживает `AI_PROXY_URL` — симметрично
Groq/Gemini, на случай если это изменится — но требованием не является.

### Известное ограничение: Gemini через этот туннель не работает

Проверено вживую (через уже существующий, отдельный туннель book library к
тому же внешнему серверу, ещё до создания собственного туннеля бота): запрос
к `api.groq.com` через прокси вернул **`401`** (реально достучались,
геоблок обойдён, просто нет ключа в тестовом запросе). Тот же самый запрос к
`generativelanguage.googleapis.com` через тот же туннель вернул **`403`** —
то есть Google блокирует не только российские IP, но, похоже, и сам этот
внешний узел целиком (типичное для Google поведение в отношении
датацентровых/VPN-адресов, не обязательно специфично для этого конкретного
сервера).

Код для Gemini через прокси (`llm/gemini_client.py`, `types.HttpOptions(client_args=
{"proxy": AI_PROXY_URL})`) написан и обоснован документацией самого SDK
(`google-genai`, README пакета прямо описывает этот рецепт), но **не
проверен живым трафиком** — на library-vps используется только
`LLM_PROVIDER=groq`. Если понадобится Gemini именно с этого VPS — нужен либо
другой внешний узел для туннеля, либо какой-то другой обход; это отдельная,
не решённая здесь задача.

### Проверка

```bash
# geo через прокси — страна внешнего сервера, не Россия
docker compose exec app python -c "import httpx; print(httpx.get('https://ipapi.co/json/', proxy='socks5h://ai-proxy:1080', timeout=15).json())"

# прямой вызов без прокси — контрольная точка, воспроизводит исходную проблему
docker compose exec app python -c "import httpx; print(httpx.get('https://api.groq.com/openai/v1/models', timeout=15).status_code)"
# ожидаемо: 403

# через туннель — геоблок обойдён
docker compose exec app python -c "import httpx; print(httpx.get('https://api.groq.com/openai/v1/models', proxy='socks5h://ai-proxy:1080', timeout=15).status_code)"
# ожидаемо: 401 (не 403 — значит реально достучались до Groq)
```

## Процедура

1. **Клон репозитория** на VPS от имени `deploy`:
   ```bash
   ssh library-vps-deploy
   git clone https://github.com/glorden/fuel-chat-bot.git ~/fuel-chat-bot
   cd ~/fuel-chat-bot
   ```
2. **Секреты и реальные данные — с машины разработчика, не через git.**
   Перед копированием БД — остановить локальный `python bot.py`, если
   запущен, и сделать checkpoint WAL в основной файл (WAL может весить
   заметно больше самого `bot.db` — большая часть накопленных данных лежит
   там, пока не сделан checkpoint):
   ```bash
   python -c "from db.schema import get_connection; get_connection().execute('PRAGMA wal_checkpoint(TRUNCATE);')"
   ```
   Затем:
   ```bash
   scp .env library-vps-deploy:~/fuel-chat-bot/.env
   scp bot.db bot.db-shm bot.db-wal library-vps-deploy:~/fuel-chat-bot/
   scp gazetteer.yaml library-vps-deploy:~/fuel-chat-bot/gazetteer.yaml
   ```
   На сервере дописать в `.env` переменные `AI_PROXY_*` (их нет в
   локальном `.env` — эта возможность появилась только при деплое). Все три
   файла БД и `gazetteer.yaml` обязаны существовать на хосте **до** первого
   `up` — иначе Docker создаст на месте bind-mount пустую директорию вместо
   файла, и приложение упадёt при старте с непонятной ошибкой вместо чёткой
   «файл не найден». На практике полный `TRUNCATE`-checkpoint убирает
   `bot.db-shm`/`bot.db-wal` целиком (не просто обнуляет) — на сервере их
   нужно создать пустыми до `up`, `scp` переносить нечего:
   ```bash
   ssh library-vps-deploy "touch ~/fuel-chat-bot/bot.db-shm ~/fuel-chat-bot/bot.db-wal"
   ```
3. **Ключ для туннеля** — на library-vps, не на машине разработчика:
   ```bash
   mkdir -p secrets
   ssh-keygen -t ed25519 -f secrets/ai_proxy_id_ed25519 -C "fuel-chat-bot-ai-proxy" -N ""
   cat secrets/ai_proxy_id_ed25519.pub
   ssh-keyscan -p 22 "$AI_PROXY_SSH_HOST" > secrets/ai_proxy_known_hosts
   ```
   Публичный ключ добавить в `authorized_keys` пользователя `tunneluser` на
   внешнем сервере (см. выше, «Внешний сервер») — это шаг на *другой* машине,
   не на library-vps, делается отдельно. Пока ключа там нет — `ai-proxy` не
   поднимется (уйдёт в краш-луп аутентификации), это ожидаемо, не повод
   дебажить дальше.

   Прежде чем тратить диск и время на сборку образов — дешёвая проверка,
   что ключ реально принят внешним сервером именно в режиме `-N`
   (единственном, который использует entrypoint.sh; `tunneluser` на
   `/usr/sbin/nologin` отклоняет обычное выполнение команд, поэтому простой
   `ssh ... echo ok` тут не тест):
   ```bash
   timeout 8 ssh -i secrets/ai_proxy_id_ed25519 \
     -o UserKnownHostsFile=secrets/ai_proxy_known_hosts \
     -o BatchMode=yes -N -p "$AI_PROXY_SSH_PORT" \
     "$AI_PROXY_SSH_USER@$AI_PROXY_SSH_HOST" &
   pid=$!; sleep 4
   kill -0 $pid 2>/dev/null && echo OK || echo FAILED
   kill $pid 2>/dev/null
   ```
4. **Первый запуск, LLM выключен** — сначала доказать, что бот вообще
   работает и говорит с VK, не трогая прокси/LLM:
   ```bash
   docker builder prune -f
   # убедиться LLM_ENABLED=false в .env
   docker compose up -d --build
   docker compose logs -f app
   ```
   Долгую сборку без прогресс-вывода SSH-сессия иногда обрывает по таймауту
   неактивности — сама сборка на стороне Docker-демона при этом продолжается
   независимо; надёжнее гонять отсоединённо и опрашивать короткими
   подключениями:
   ```bash
   nohup docker compose up -d --build > /tmp/build.log 2>&1 & disown
   ```
   Проверить: `docker compose ps` (`app`+`ai-proxy` оба `Up`), реальное
   сообщение в беседе обрабатывается rule-based-путём, `df -h /`/`docker
   stats --no-stream`/`docker ps -a` (чужие контейнеры не задеты).
5. **Проверка туннеля** — см. «Проверка» выше. Убедиться, что третий вызов
   даёт `401`, не `403`, прежде чем включать LLM.
6. **Включение LLM**: в `.env` — `LLM_ENABLED=true`, `LLM_PROVIDER=groq`
   (прописать явно, не полагаться молча на дефолт). Обычный `restart` не
   перечитывает `env_file` — нужен `--force-recreate`:
   ```bash
   docker compose up -d --force-recreate app
   docker compose logs -f app | grep -E "path=(llm|rule_based)"
   ```
   На реальном трафике должны появляться строки `path=llm`, не сплошной
   `path=rule_based reason=llm_fallback`.
7. **Живая проверка в чате**: тегнуть бота реальным вопросом в беседе,
   сверить и ответ, и соответствующую строку лога. Не обязательно
   тегать самому — можно просто последить `docker compose logs -f app`
   (фильтровать на `path=|outcome=|Traceback|ERROR`) на органическом трафике
   беседы: реальных тематических сообщений обычно достаточно за 5-10 минут,
   и это заодно живая проверка на разнообразных, не подготовленных заранее
   формулировках.
8. **Бэкапы** — см. ниже, сознательно не решено в рамках базового деплоя.

## Операционные нюансы

- **SSH-сессия может обрываться на длинных «тихих» командах** (см. шаг 4) —
  гонять сборку отсоединённо, не полагаться на одну долгоживущую сессию.
- **Диск на этом VPS может забиться build-кэшем** — `docker builder prune -f`
  освобождает место без потери уже собранных образов (в том числе чужих).
- **`restart` vs `--force-recreate`**: `env_file:` читается на пересоздание
  контейнера, не на обычный `restart` — после правки `.env` нужен
  `--force-recreate` (или `down && up`), иначе изменения тихо не применятся.
- **`gazetteer.yaml` правится вручную прямо на сервере** (см. CLAUDE.md) —
  bind-mount, не пересобирается из образа; изменения подхватываются на
  следующий рестарт контейнера `app` (файл читается при старте, не
  отслеживается на лету).

## Бэкапы

**Сознательно не часть этого деплоя.** Как и у book library — решение
отложено. Открытый риск: без бэкапа вне VPS `bot.db` (накопленная история
отчётов, `unresolved_mention`, `station_break`, `fuel_limit`) не защищена от
потери самого VPS. `gazetteer.yaml` менее критичен — он же version-controlled
в git, восстановим из репозитория.
